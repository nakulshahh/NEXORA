## Why it exists

Once you have many containers on many machines, someone must decide where each runs, restart those that die, replace versions without downtime and give them stable addresses. Orchestrators automate this. Kubernetes is the dominant one.

<Callout kind="why">
The core idea is a **control loop**: you declare the desired state ("3 replicas of image v2"), and controllers continuously compare it with reality and act to close the gap.
</Callout>

## How it works

**Verification status:** there is no Kubernetes cluster in the development sandbox, so none of this lesson's behaviour was reproduced here. It follows the official documentation linked above; try it on a local cluster (kind or minikube) to see it happen.

### The objects

- **Pod**: one or more containers sharing a network and storage; the smallest schedulable unit. Pods are disposable and have changing IP addresses.
- **Deployment**: declares the desired number of identical pods and the image version; it creates a ReplicaSet that keeps that many alive.
- **Service**: a stable name and virtual IP that load-balances to the ready pods matching a label, so callers do not track pod addresses.
- **Node**: a machine in the cluster. The **scheduler** places each pod on a node that has the resources it **requests**; **limits** cap what it may use (exceeding memory gets it killed with 137, as in the Docker chapter).
- **Ingress** or gateway: routes external HTTP traffic to services.
- **ConfigMap and Secret**: configuration and sensitive values injected as environment variables or files (B11).

### Probes

- **Readiness probe**: is this pod ready for traffic? Failing pods are removed from the Service endpoints (it is the "not ready" signal from the graceful-shutdown lesson).
- **Liveness probe**: is it stuck beyond recovery? Failing pods are restarted. Keep it cheap and independent of dependencies, or a database blip restarts every pod at once.
- **Startup probe**: allows slow starts without liveness killing the pod.

### Rolling updates

Changing the image in a Deployment starts a rollout: new pods start, and once ready, old pods are terminated, controlled by `maxSurge` and `maxUnavailable`. Terminating a pod runs the sequence from the graceful-shutdown lesson: removed from endpoints, SIGTERM, grace period, SIGKILL. If the new version never becomes ready, the rollout stalls and the old pods keep serving; `kubectl rollout undo` returns to the previous version. This is why readiness probes and graceful shutdown are what make deploys safe.

### Is it worth it?

Kubernetes costs a learning curve, cluster operations (or a managed service's price) and a lot of YAML. It pays when you have many services, need autoscaling, multi-team self-service or portability. Alternatives: a platform-as-a-service, managed container services, or Compose on a VM.

## Common mistakes

<Callout kind="mistake">
Setting no resource requests and limits. The scheduler cannot place pods sensibly, one pod can starve its neighbours, and overloaded nodes evict pods unpredictably.
</Callout>

- **Liveness probes that depend on the database.**
- **Skipping readiness probes**, so rollouts send traffic to unready pods.
- **Latest tags** and no rollout history.
- **Putting state in pods** without persistent storage.
- **Adopting Kubernetes for one service.**

## Trade-offs

<Callout kind="tradeoff">
You get declarative deploys, self-healing and a large ecosystem, and pay in complexity, cost and a new category of failure (misconfigured probes, resource limits, networking). The control loop is also eventually consistent: changes take seconds to propagate.
</Callout>

## In production

<Callout kind="prod">
Use managed control planes where possible, set requests, limits and probes for every workload, run at least two replicas across zones, protect rollouts with PodDisruptionBudgets, keep manifests in version control and apply them through CI, and test node and pod failure before relying on self-healing.
</Callout>
