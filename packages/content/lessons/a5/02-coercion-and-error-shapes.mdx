## Why it exists

Validation (the previous lesson) decides what is acceptable. This lesson covers the awkward middle step: turning loosely typed input into the exact types your code wants, and telling the caller clearly when that fails.

JSON preserves numbers, booleans and null. A query string preserves nothing: `/items?limit=10&active=true` delivers the text `"10"` and the text `"true"`. Path parameters, headers and form bodies are text too.

<Callout kind="why">
Convert once, in the same place you validate, so the rest of the code receives real numbers and booleans and never has to wonder.
</Callout>

## How it works

### JavaScript's conversions are forgiving

```js file=coercion.mjs mark=1,2
console.log(Number(""), Number("  "), Number(null), Number(undefined));
console.log(Number("12abc"), parseInt("12abc"), Number("0x10"), Number("1e3"));
```

This prints `0 0 0 NaN` and then `NaN 12 16 1000`. An empty string becomes `0`, `parseInt` stops at the first bad character and returns `12` for `"12abc"`, and hexadecimal and exponent forms are accepted. If `?limit=` (empty) quietly becomes `0`, your pagination silently misbehaves. Check the string with a pattern first, then convert:

```js file=parse-limit.mjs mark=2,3
function parseLimit(raw, { def = 20, max = 100 } = {}) {
  if (raw === undefined) return { ok: true, value: def };
  if (typeof raw !== "string" || !/^\d{1,4}$/.test(raw)) return { ok: false, error: "limit must be a whole number" };
  const n = Number(raw);
  if (n < 1 || n > max) return { ok: false, error: `limit must be between 1 and ${max}` };
  return { ok: true, value: n };
}
```

Defaults are applied here, in one place, instead of being scattered as `limit || 20` across handlers. (`||` is a classic bug source: it also replaces a legitimate `0`.)

### Repeated and unknown keys

The same key can appear twice. With the standard URL API, `get` returns the first value and `getAll` returns every value:

```js file=repeated.mjs mark=2,3
const q = new URL("http://h/items?limit=10&limit=20").searchParams;
console.log(q.get("limit"), q.getAll("limit")); // 10 [ '10', '20' ]
```

Frameworks differ in what they hand you (a string, the last value, or an array), so a validator should say which it accepts and reject the rest.

For **unknown fields** in a JSON body choose a policy deliberately: *strip* them (lenient, common for public APIs), or *reject* them (strict, catches typos such as `emial`). Either is fine; accidentally passing them through is not.

### Duplicate keys in JSON

JSON text such as `{"a":1,"a":2}` parses to `{ a: 2 }` in JavaScript: the last one wins. Other languages may keep the first. If two components disagree about which wins, an attacker can show one value to a checker and another to the code that acts on it. Parse once and pass the parsed object around, never the raw text.

### Error responses

Return **400 Bad Request** for malformed or invalid input (some teams use **422 Unprocessable Content** for "well-formed but semantically invalid"; pick one and be consistent). Include enough for a client to fix the request, and nothing about your internals:

```json file=error.json mark=2,3
{
  "error": { "code": "validation_failed", "message": "Invalid request" },
  "fields": { "limit": "limit must be between 1 and 100" }
}
```

A stable machine-readable `code`, a human message, and per-field details. RFC 9457 standardises a similar "problem details" shape if you want an existing convention.

## Common mistakes

<Callout kind="mistake">
Using `parseInt` or `Number` straight on user input and trusting the result. `parseInt("12abc")` is 12 and `Number("")` is 0: the bad input became a plausible value.
</Callout>

- **Using `||` for defaults**, which also overrides `0` and the empty string.
- **Leaking internals** in errors: stack traces, SQL fragments or file paths.
- **Different error shapes per endpoint**, which forces every client to special-case each route.
- **Returning 200 with an error in the body**, which breaks caches, monitoring and generic clients.

## Trade-offs

<Callout kind="tradeoff">
Strict conversion ("must be digits only") gives precise errors but rejects `limit=10.0` or `limit=+10`. Lenient conversion accepts more but multiplies the ways one value can be written, which makes caching, logging and security rules harder. Public APIs lean strict and document the exact format.
</Callout>

## In production

<Callout kind="prod">
Put coercion and defaults in the schema so they are declared, tested and documented in one place. Cap array lengths, string lengths and pagination sizes. Count validation failures per route and per client in your metrics.
</Callout>
