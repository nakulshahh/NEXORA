## Why it exists

Sessions need a lookup in a shared store on every request. A **JSON Web Token** carries the identity inside itself, signed by the server, so any server copy can verify it with a key and no store. That is attractive for many servers, or for several services that should all accept the same login.

<Callout kind="why">
The token moves the state from the server to the client and replaces a lookup with a signature check.
</Callout>

## How it works

### The three parts

A JWT is three base64url pieces joined by dots: **header** (algorithm), **payload** (claims such as user id and expiry), and **signature**. The signature is computed over the first two with a secret (or a private key). On each request the server recomputes it. If the payload were altered, the signature would not match.

```js file=jwt-sketch.mjs mark=4,5,9
import { createHmac, timingSafeEqual } from "node:crypto";

const b64 = (o) => Buffer.from(JSON.stringify(o)).toString("base64url");
const sign = (data, secret) =>
  createHmac("sha256", secret).update(data).digest("base64url");

export function issue(claims, secret) {
  const body = `${b64({ alg: "HS256", typ: "JWT" })}.${b64(claims)}`;
  return `${body}.${sign(body, secret)}`;
}

export function verify(token, secret) {
  const [h, p, s] = token.split(".");
  const expected = Buffer.from(sign(`${h}.${p}`, secret));
  const given = Buffer.from(s ?? "");
  if (expected.length !== given.length || !timingSafeEqual(expected, given)) return null;
  const claims = JSON.parse(Buffer.from(p, "base64url").toString());
  return claims.exp > Date.now() / 1000 ? claims : null;
}
```

<Callout kind="note">
This is a teaching sketch. In real code, use a maintained JWT library, pin the accepted algorithm yourself, and never accept the algorithm named in an incoming token header blindly. Accepting "none" or a swapped algorithm has caused real breaches.
</Callout>

### What it does not do

The payload is readable by anyone. Do not put secrets in it. And because no server record exists, you cannot simply delete a token: it stays valid until it expires. The usual compromise is a **short-lived access token** (minutes) plus a **refresh token** stored server-side that can be revoked and exchanged for new access tokens.

JWTs shine when verification must happen in many places without a shared database. For one ordinary web app, a server-side session is simpler and easier to revoke. Choose with a reason, not a trend.

### Authorization

Once you know who is calling, check what they may do:

- **Role-based**: admins may delete users, members may not.
- **Ownership**: a user may read **their own** invoice.

```js file=route.mjs mark=3,4,5
app.get("/invoices/:id", requireLogin, async (req, res) => {
  const invoice = await db.invoice.findById(req.params.id);
  if (!invoice || invoice.ownerId !== req.user.id) {
    return res.status(404).end(); // same answer for missing and forbidden
  }
  res.json(invoice);
});
```

Skipping the ownership line is the classic **IDOR** (insecure direct object reference): any logged-in user changes the number in the URL and reads someone else's data. Returning 404 for both missing and forbidden avoids revealing which ids exist.

## Common mistakes

<Callout kind="mistake">
Checking only that a user is logged in, not that they own the object. This is among the most common serious API bugs, because the code works perfectly in testing with one user.
</Callout>

- **Long-lived JWTs with no revocation path.**
- **Storing a token where scripts can read it** (such as localStorage) without weighing the cross-site scripting risk, versus an HttpOnly cookie.
- **Trusting claims such as `role: admin` that the client could have forged**, when the signature is not actually verified.
- **Doing authorization only in the UI**, by hiding buttons.

## Trade-offs

<Callout kind="tradeoff">
Sessions: easy revocation, a lookup per request, shared store required. JWTs: no lookup and easy to verify anywhere, but hard to revoke and larger on every request. Many systems use both: a short JWT at the edge, a revocable refresh session behind it.
</Callout>

## In production

<Callout kind="prod">
Keep signing keys in a secrets manager and support key rotation. Keep access tokens short, log authorization failures, and write tests that log in as user A and try to read and change user B's objects. That one test finds more real bugs than most reviews.
</Callout>
