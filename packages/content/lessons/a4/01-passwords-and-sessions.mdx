## Why it exists

HTTP forgets everything between requests. Yet an app must know that this request comes from the same person who logged in a minute ago, and it must not trust a client that simply claims "I am user 7". Two separate problems follow:

- **Authentication**: proving who the caller is.
- **Authorization**: deciding what that caller may do.

This lesson covers authentication. The next covers tokens and authorization.

<Callout kind="why">
Authentication is the first thing an attacker targets and the thing users reuse across sites, so mistakes here leak accounts everywhere.
</Callout>

## How it works

### Storing passwords

Never store the password. Store the output of a **password hash**: a one-way function made deliberately slow and memory-hungry (scrypt, argon2, bcrypt). Add a random **salt** per user so equal passwords produce different hashes and precomputed tables are useless.

```js file=password.mjs mark=5,6,11,12
import { scryptSync, randomBytes, timingSafeEqual } from "node:crypto";

export function hash(password) {
  const salt = randomBytes(16);
  const key = scryptSync(password, salt, 32);
  return `${salt.toString("hex")}:${key.toString("hex")}`;
}

export function verify(password, stored) {
  const [saltHex, keyHex] = stored.split(":");
  const key = scryptSync(password, Buffer.from(saltHex, "hex"), 32);
  return timingSafeEqual(key, Buffer.from(keyHex, "hex"));
}
```

Slowness is the point: a legitimate login hashes once, which costs tens of milliseconds, while an attacker with a stolen table must try billions of guesses. `timingSafeEqual` avoids leaking how many leading bytes matched through response time.

<Callout kind="note">
Real systems usually use a vetted library for argon2 or bcrypt so parameters and encoding are handled for you. The example shows the idea with what ships in Node.
</Callout>

### Sessions

After the password check succeeds, the server creates a **session**: a record such as `{ id, userId, expiresAt }` in a store, keyed by a long random id. It sends the id to the browser in a cookie. Every later request carries the cookie, the server looks the id up, and finds the user.

The id must be unguessable: 128 bits or more from a cryptographic random source. Because the server holds the state, it can **revoke** instantly: delete the record and the cookie stops working.

### Cookie flags

```http file=set-cookie.http mark=1
Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

- **HttpOnly**: scripts cannot read it, limiting the damage of cross-site scripting.
- **Secure**: sent only over HTTPS.
- **SameSite**: restricts sending on cross-site requests, a main defence against cross-site request forgery. See the CORS lesson for how it differs from cross-origin rules.
- **Max-Age / Expires**: bounds the session lifetime.

## Common mistakes

<Callout kind="mistake">
Putting the user id itself in the cookie (`uid=7`). A client can change it to 8. The cookie must be an opaque random id that only means something inside your server's store.
</Callout>

- **Fast hashes** such as plain SHA-256 for passwords, which attackers compute at billions per second.
- **Telling the user which half was wrong.** "No such email" versus "wrong password" lets attackers enumerate accounts. Return one generic message.
- **No login rate limiting**, which permits unlimited guessing.
- **Not rotating the session id after login**, which enables session fixation.

## Trade-offs

<Callout kind="tradeoff">
Server-side sessions are easy to revoke and keep secrets off the client, but every request needs a lookup and the store becomes shared infrastructure that must be fast and available across all server copies. Putting sessions in a fast store such as Redis is the common answer.
</Callout>

## In production

<Callout kind="prod">
Run the session store outside the app processes so every copy sees the same sessions, set a sensible idle and absolute expiry, delete sessions on logout and on password change, and log sign-ins and failures. Prefer a maintained auth library or a hosted identity service to hand-rolled code.
</Callout>
