## Why it exists

Between your own services you control both ends, so the flexibility of human-readable JSON buys less and costs bytes, parsing time and runtime type errors. A contract-first approach gives generated clients and servers in many languages, typed errors at build time and streaming.

<Callout kind="why">
gRPC trades the browser-friendly, debug-by-eye simplicity of REST for strict contracts, efficient encoding and streaming between services you own.
</Callout>

## How it works

### The contract

You describe messages and services in a `.proto` file; tools generate code for each language:

```proto file=user.proto mark=2,3,4,5
message User {
  int64  id     = 1;
  string name   = 2;
  bool   active = 3;
  int64  score  = 4;
}
service Users { rpc GetUser (GetUserRequest) returns (User); }
```

The numbers (`= 1`) are **field numbers**: the identity of a field on the wire.

### What the bytes look like

Encode `{id: 150, name: "Ada", active: true, score: 300}`. Each field is a key (field number and type), then the value. Integers use a **varint**: seven bits per byte, with the high bit saying "more bytes follow". 1 is `01`, 150 is `96 01`, 300 is `ac 02`.

```text file=bytes.txt
08 96 01        field 1 (varint) = 150
12 03 41 64 61  field 2 (length 3) = "Ada"
18 01           field 3 (varint) = true
20 ac 02        field 4 (varint) = 300
total: 13 bytes

JSON: {"id":150,"name":"Ada","active":true,"score":300}  =  49 bytes
```

I computed those bytes by hand-encoding the format in a script; the protobuf documentation's encoding guide shows the same scheme. Here protobuf is 13 bytes against JSON's 49, about a quarter. Small numbers cost one byte, names cost none. The saving shrinks for text-heavy payloads and grows for number-heavy ones, and gzip narrows the gap for JSON.

### gRPC on top

gRPC sends these messages over **HTTP/2**: many concurrent calls on one connection, header compression, and four call shapes: unary (one request, one response), server streaming, client streaming and bidirectional streaming. Calls carry **deadlines** that propagate downstream, and a defined set of status codes. Because of HTTP/2 framing and trailers, browsers cannot call gRPC directly; use gRPC-Web or a gateway, and keep REST/JSON for public APIs.

### Evolving a schema

- Add new fields with **new numbers**; old readers ignore unknown fields.
- Never reuse or renumber a field number; mark removed ones `reserved`.
- Do not change a field's type incompatibly.
- Treat missing fields as defaults, since protobuf3 does not tell "unset" from zero without the `optional` keyword.

Run a compatibility check in CI so a breaking change fails the build.

## Common mistakes

<Callout kind="mistake">
Renumbering fields or reusing a deleted field's number. Old messages in queues or caches are then decoded as the wrong field, silently corrupting data.
</Callout>

- **No deadline on calls**, repeating the timeout mistakes from the fault-tolerance lessons.
- **Exposing internal gRPC directly to browsers.**
- **Huge messages**; stream or paginate instead.
- **Treating zero as "missing"** for numeric fields.
- **Adopting gRPC for a two-service system** where a plain HTTP call is simpler.

## Trade-offs

<Callout kind="tradeoff">
gRPC gives strong contracts, smaller payloads and streaming; you pay with tooling, a build step, harder debugging (binary payloads) and no direct browser support. REST/JSON is easy to inspect and universal, at a cost in bytes and looser types. Many systems use REST at the edge and gRPC inside.
</Callout>

## In production

<Callout kind="prod">
Set deadlines and retry policy per method, enable server reflection or keep protos in a shared repository, version services deliberately, propagate trace and request ids in metadata, and use a load balancer that understands HTTP/2 (long-lived connections defeat naive connection-level balancing).
</Callout>
