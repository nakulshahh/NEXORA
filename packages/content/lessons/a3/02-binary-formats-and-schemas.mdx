## Why it exists

JSON repeats every field name in every message and writes numbers as text. For a service that sends millions of small messages to another service, that is wasted bandwidth and CPU. A **schema-based binary format** agrees the field layout in advance, so the message carries only values and short numeric tags.

<Callout kind="why">
When both sides share a schema, names do not need to travel. That is where the size and speed come from, and also where the new problems come from.
</Callout>

## How it works

### Varints: small numbers take fewer bytes

A **varint** stores an unsigned integer 7 bits at a time. Each byte holds 7 bits of the number; the top bit says "more bytes follow". Small numbers fit in one byte.

```js file=varint.mjs mark=2,3,4,5
export function encodeVarint(n) {
  const out = [];
  while (n >= 0x80) { out.push((n & 0x7f) | 0x80); n = Math.floor(n / 128); }
  out.push(n);
  return Uint8Array.from(out);
}
// 1   -> 01
// 300 -> ac 02   (300 = 0b10_0101100: low 7 bits 0101100 with the continue bit set = 0xac, then 0b10 = 0x02)
```

I ran this: `1` encodes as `01` and `300` as `ac 02`. The cost is one byte per 7 bits of the value, so the size depends on how large the number is, not on the field type.

### A whole message by hand

Take the schema `message User { int32 id = 1; string name = 2; }` and the value `{ id: 150, name: "ada" }`. Each field is written as a **tag** (the field number shifted left 3 bits, OR the wire type) followed by its value.

| Bytes | Meaning |
|---|---|
| `08` | tag: field 1, wire type 0 (varint) |
| `96 01` | varint 150 |
| `12` | tag: field 2, wire type 2 (length-delimited) |
| `03` | length 3 |
| `61 64 61` | the UTF-8 bytes of "ada" |

Total: `08 96 01 12 03 61 64 61` is **8 bytes**. The equivalent JSON text `{"id":150,"name":"ada"}` is 23 bytes. (Both counts were produced by running the code.)

### Why field numbers are forever

The reader uses the tag to know which field it is looking at. That makes **evolution** possible if you follow the rules:

- **Safe:** add a new field with a new number (old readers skip unknown tags); stop using a field and mark its number **reserved**; rename a field (names are not on the wire).
- **Breaking:** reuse a number for a different meaning; change a field's type to an incompatible one.

### The cost you accept

You cannot read the bytes with your eyes, you need the schema and code generation, and tooling like curl and browser dev tools understand JSON better than Protobuf. That is the real price of the savings.

## Common mistakes

<Callout kind="mistake">
Reusing a retired field number for a new field. An old client that still sends the old meaning will write data the new server interprets as the new meaning, and nothing fails loudly.
</Callout>

- **Making every field required.** You can never remove one later. Treat fields as optional by default.
- **Switching formats for speed without measuring.** Network and database time usually dominate parsing time.
- **Using floats for money** in a schema as well, with the same errors as JSON.

## Trade-offs

<Callout kind="tradeoff">
Binary formats reduce size and parse time and give strong contracts, at the price of tooling, readability and a build step. They shine for internal service-to-service calls at high volume. Public, browser-facing APIs usually stay on JSON.
</Callout>

## In production

<Callout kind="prod">
Schema files live in version control with a compatibility check in CI (tools such as buf compare the new schema to the previous release and fail on breaking changes). Retired field numbers are marked reserved so nobody reuses them. gRPC, covered in a later chapter, is built on exactly this.
</Callout>
