## Why it exists

The A4 and A5 chapters established "never trust input". This lesson shows what that costs when ignored and the two fixes that matter most in practice.

<Callout kind="why">
Security work is mostly closing a small number of well-known holes systematically. Each one below has a cheap, standard defence that you should apply without exception.
</Callout>

## How it works

### SQL injection

Building a query by gluing strings lets the input change the query's structure. Input `' OR '1'='1` against a lookup by name, on a table of three customers:

```text file=sqli.txt
concat query:   select name from customers where name = '' OR '1'='1'
rows returned:  3 of 3 customers      <- the filter vanished
parameterized:  0 rows                 <- the input was just a (non-matching) name
```

The fix is to keep code and data separate:

```ts file=param.ts mark=1
const r = await pool.query("SELECT name FROM customers WHERE name = $1", [input]);
```

The driver sends the statement and the value separately, so the value is never parsed as SQL. Parameters cannot place identifiers (table or column names); for those, choose from an allow-list in code. ORMs and query builders parameterise by default, but a raw-SQL escape hatch with a template string reopens the hole.

### Storing passwords

If your database leaks, the stored values decide whether passwords leak. Measured on one core of the sandbox:

| Scheme | Time per hash | Guesses per second per core |
| --- | --- | --- |
| SHA-256 | about 0.0025 ms | about 720 000 |
| scrypt (N=16384) | about 38 ms | about 32 |

That is a factor of about 20 000. A **slow, memory-hard hash** (scrypt, Argon2id, or bcrypt) makes each guess expensive. A unique random **salt** per password stops attackers precomputing tables and from cracking identical passwords together. Compare hashes with a constant-time function (`crypto.timingSafeEqual`), and re-hash on login if parameters are upgraded. Do not invent your own scheme.

### The trust boundary

Everything that arrives over the network is attacker-controlled: body, headers, cookies, URL, even the `User-Agent`. Validate at the edge (A5), authorise every request on the server (A4), and never decide authority from client-supplied values such as `isAdmin: true` or a price in the request. Anything you send *to* the client (error messages, stack traces, ids) is also a disclosure decision.

### Least privilege

The application's database role should not be a superuser. Give it only the rights it needs, use a separate role for migrations, keep secrets in the environment or a secret store (never in the repository), and scope API tokens narrowly. A compromised component should be able to do only what that component needed.

## Common mistakes

<Callout kind="mistake">
Logging full request bodies or tokens "for debugging". Logs spread widely and last long; secrets in logs are a common cause of real breaches.
</Callout>

- **String-built SQL** in one "temporary" admin query.
- **Fast hashes or unsalted hashes** for passwords.
- **Returning detailed errors** (SQL text, stack traces) to clients.
- **Trusting hidden form fields** or client-computed totals.
- **One shared superuser** database account for everything.
- **Committing `.env` files** or keys to version control.

## Trade-offs

<Callout kind="tradeoff">
Slow hashes cost CPU on every login and can be a denial-of-service lever if unprotected, so rate-limit logins and size the work factor to a login taking tens of milliseconds, not seconds. Strict least-privilege roles mean more setup and occasional permission errors, in exchange for a smaller blast radius.
</Callout>

## In production

<Callout kind="prod">
Run dependency and secret scanning in CI, rotate credentials on a schedule and after any suspected exposure, keep separate credentials per environment, and test your login path under load with the real hash cost.
</Callout>
