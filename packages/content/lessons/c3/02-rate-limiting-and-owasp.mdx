## Why it exists

Even a correct, well-validated API can be hammered: a script guessing passwords, a client in a retry loop, a scraper. Limits keep one actor from consuming the shared capacity, and the Top 10 keeps you honest about the boring failures that cause most breaches.

<Callout kind="why">
Defence in depth: validation stops bad input, authorisation stops bad actors, limits stop bad volume. Each layer assumes the others can fail.
</Callout>

## How it works

### The token bucket

A bucket holds up to `capacity` tokens and refills at `rate` tokens per second. Each request takes one token; with none left the request is rejected with **429 Too Many Requests**. This allows short bursts (up to the capacity) while enforcing an average rate.

```ts file=bucket.ts mark=3,4,5
function bucket(rate: number, capacity: number) {
  let tokens = capacity, last = 0;
  return (now: number) => {
    tokens = Math.min(capacity, tokens + (now - last) * rate);
    last = now;
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
  };
}
```

With rate 5 per second and capacity 10, firing 100 requests in one second (100 per second): 14 were allowed (the 10 in the bucket plus the roughly 4 it refilled), and 86 were rejected. The bound is capacity plus rate times time.

Alternatives: a **fixed window** counter (simple, but allows double the limit across a window boundary) and a **sliding window** (smoother, a bit more state).

### Where state lives

An in-process counter (the default in most rate-limit libraries) is per instance: with four instances behind a load balancer an attacker effectively gets four times the limit, and a restart resets it. For a real limit the state must be **shared**: a Redis `INCR` with an expiry is the classic, or a Postgres table when you want no extra infrastructure. A shared store must be fast and must decide what to do when it is down (fail open and risk abuse, or fail closed and risk an outage).

### What to key on

Per **user** or API key (fair, and survives shared IPs), per **IP** (needed before login, but many users share one IP behind a NAT), and per **endpoint** (login and password-reset are far more sensitive than reading a list). Return `Retry-After` so well-behaved clients can slow down.

### The OWASP Top 10, as a checklist

- **Broken access control**: check the owner on every object access (the IDOR from A4). Most common.
- **Cryptographic failures**: TLS everywhere, slow password hashes, no secrets in URLs.
- **Injection**: parameterised queries, the previous lesson.
- **Insecure design and misconfiguration**: debug modes off, default credentials changed, minimal exposed surface, security headers.
- **Vulnerable components**: scan and update dependencies.
- **Authentication failures**: rate-limit logins, no user enumeration in error messages.
- **Integrity failures and logging gaps**: verify what you deploy, log security events.
- **SSRF** (server-side request forgery): when your server fetches a URL a user supplied, block internal addresses such as the cloud metadata endpoint.

## Common mistakes

<Callout kind="mistake">
Rate limiting only by IP behind a proxy without configuring trusted proxy headers: every request then appears to come from the proxy's address, so everyone shares one bucket, or the limit is trivially spoofed with an `X-Forwarded-For` header you should not trust.
</Callout>

- **Limits only in the web app**, not on the API behind it.
- **Different error messages** for "no such user" and "wrong password", which enables enumeration.
- **Counting only failures** so credential stuffing across many accounts slips through.
- **Fail-open limiter** that silently disables protection during an outage of the shared store.
- **Forgetting expensive endpoints** (search, export, AI) that need tighter limits.

## Trade-offs

<Callout kind="tradeoff">
Strict limits block abuse and also legitimate bursts (an office behind one IP). Shared state is accurate but adds a dependency and latency to every request; local limits are fast and approximate. Choose per endpoint and measure false positives.
</Callout>

## In production

<Callout kind="prod">
Expose limit headers, monitor 429 rates by route and key, alert on sudden jumps in 401/403 and 429, keep an allow-list for trusted internal callers, and review the Top 10 against each service at design time and after major changes.
</Callout>
