## Why it exists

Storing a customer's name inside every one of their orders repeats data and invites contradictions. The relational model's answer is to keep each kind of fact in its own **table** and refer between tables by **key**. The database then guarantees the references stay valid, and a query recombines the pieces when you need them together.

<Callout kind="why">
Constraints turn rules ("an order belongs to a real customer", "a total is never negative") from hopes in application code into facts the database enforces for every writer.
</Callout>

## How it works

The examples below run on PostgreSQL.

```sql file=schema.sql mark=1,2,3
CREATE TABLE customers (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE orders (
  id          int PRIMARY KEY,
  customer_id int REFERENCES customers(id),
  total       int NOT NULL CHECK (total >= 0)
);
INSERT INTO customers VALUES (1,'Asha'),(2,'Ben'),(3,'Chen');
INSERT INTO orders VALUES (10,1,50),(11,1,70),(12,2,20),(13,NULL,5);
```

- A **primary key** uniquely identifies a row and cannot be NULL.
- A **foreign key** (`REFERENCES`) says this column must match a row in another table. Violating it fails:

```text file=fk-error.txt
INSERT INTO orders VALUES (14, 99, 1);
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(99) is not present in table "customers".
```

- `NOT NULL` and `CHECK` reject bad values the same way (`total = -1` fails with a check-constraint error).

### Joins

An **inner join** returns only rows that match on both sides. A **left join** keeps every row from the left table and fills the right side with NULL when nothing matches.

```sql file=joins.sql mark=1,4
SELECT c.name, count(o.id) AS orders, coalesce(sum(o.total), 0) AS spent
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name ORDER BY c.name;
```

The result is Asha 2 orders / 120, Ben 1 / 20 and Chen 0 / 0. Chen appears because of the left join; with an inner join Chen, who has no orders, would vanish, and so would order 13, which has no customer. Counting `o.id` (not `*`) is what gives Chen a zero, because `count(column)` skips NULLs while `count(*)` counts rows. On the orders table, `count(*)` is 4 but `count(customer_id)` is 3.

### NULL means unknown

```sql file=null.sql mark=1,2,3
SELECT NULL = NULL;                       -- NULL, not true
SELECT NULL IS NULL;                      -- true
SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);
-- zero rows! orders.customer_id contains a NULL
SELECT name FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
-- Chen
```

SQL has **three-valued logic**: true, false and unknown. `x NOT IN (1, 2, NULL)` can never be true, because "not equal to NULL" is unknown. The query for customers with no orders silently returned nothing. `NOT EXISTS` handles it correctly. Use `IS NULL` / `IS NOT NULL` to test for NULL.

## Common mistakes

<Callout kind="mistake">
Using `NOT IN` with a subquery that can return NULL. It returns no rows and raises no error, so the bug looks like "there is no data".
</Callout>

- **Missing foreign keys** "for performance", then cleaning up orphan rows forever.
- **Inner join when you needed a left join**, silently dropping rows with no match.
- **Filtering the right table in `WHERE` after a left join**, which turns it back into an inner join; put the condition in the `ON` clause.
- **Joining without a proper condition**, producing a cross product of every pair of rows.
- **Using floating point for money**; use integers of the smallest unit or `numeric`.

## Trade-offs

<Callout kind="tradeoff">
Constraints cost a little on every write and make some bulk loads and schema changes more careful. They buy correctness that no amount of application testing guarantees. Skip a constraint only when you have a specific, measured reason, and write down what you gave up.
</Callout>

## In production

<Callout kind="prod">
Declare primary keys, foreign keys, `NOT NULL` and `CHECK` constraints in migrations, index foreign-key columns you join or delete by, and decide per foreign key what deleting a parent should do (restrict, cascade or set null) rather than taking the default by accident.
</Callout>
