## Why it exists

An API is a contract used by code you do not control. Without conventions every endpoint invents its own verbs (`/getUser`, `/doPaymentNow`) and every client must learn each one. HTTP already provides a vocabulary: URLs name things, methods say what to do with them, status codes say what happened. Using it consistently lets caches, proxies, client libraries and new teammates behave correctly without special knowledge.

<Callout kind="why">
Predictability is the product of an API. When a method means what its name says, a client can retry, cache or batch it safely without reading your documentation.
</Callout>

## How it works

### Nouns in the URL, verbs in the method

| Request | Meaning |
|---|---|
| `GET /orders/42` | read order 42 |
| `GET /orders?status=open` | list orders, filtered |
| `POST /orders` | create a new order; the server chooses its id |
| `PUT /orders/42` | replace order 42 entirely with the body |
| `PATCH /orders/42` | change only the fields in the body |
| `DELETE /orders/42` | remove order 42 |

Use plural collections and nest only to express real ownership (`/orders/42/items`). Avoid verbs in paths; when an action does not fit a noun (`cancel an order`), model it as a sub-resource or a state change (`POST /orders/42/cancellation`) rather than inventing `/cancelOrder`.

### Safe and idempotent

- A method is **safe** if it does not change server state: `GET`, `HEAD`, `OPTIONS`.
- A method is **idempotent** if doing it N times leaves the same state as doing it once: `GET`, `PUT`, `DELETE` (and the safe ones). `POST` is not, and `PATCH` is not guaranteed to be.

This is not trivia: it decides what a client or proxy may do after a timeout, when it cannot know whether the request arrived.

### Status codes that tell the truth

| Code | Use it when |
|---|---|
| 200 OK | success with a body |
| 201 Created | `POST` made a resource; add a `Location` header with its URL |
| 204 No Content | success, nothing to return (often `DELETE`, `PUT`) |
| 400 Bad Request | malformed or invalid input |
| 401 / 403 | not authenticated / authenticated but not allowed |
| 404 Not Found | no such resource |
| 409 Conflict | valid request that clashes with current state (duplicate, version mismatch) |
| 422 Unprocessable Content | well-formed but fails semantic rules (some teams use 400 instead; be consistent) |
| 429 Too Many Requests | rate limited; add `Retry-After` |

### Making POST safe to retry

A client sends `POST /payments`, the connection drops, and it does not know whether the payment happened. If it retries blindly it may charge twice. The standard remedy is an **idempotency key**: the client generates a unique value per *intended* operation and sends it in a header such as `Idempotency-Key`. The server stores the first result under that key and returns the stored result for any repeat:

```js file=idempotency.mjs mark=1,2,3,4
const seen = new Map(); let charges = 0;
function pay(key, amount) {
  if (seen.has(key)) return seen.get(key);          // repeat: same answer, no second charge
  charges += amount;
  const res = { status: 201, charged: amount };
  seen.set(key, res);
  return res;
}
// pay("k1", 50) twice returns the same response and charges = 50, not 100
```

Calling `pay("k1", 50)` twice returns the identical response both times and `charges` ends at 50. A production version stores keys in the database in the **same transaction** as the charge, expires them after a day or so, and rejects a key reused with a different body.

## Common mistakes

<Callout kind="mistake">
Returning 200 for everything and putting the real outcome in the body. Clients, proxies, caches and monitoring all key off the status line, so a "200 with an error" is invisible to all of them.
</Callout>

- **Verbs in URLs** (`POST /deleteUser`) and everything tunnelled through `POST`.
- **Changing state with `GET`**, so a link prefetcher or crawler triggers deletions.
- **`PUT` that behaves like `PATCH`**, quietly keeping old fields when the contract said "replace".
- **404 versus 403 confusion**: sometimes you deliberately return 404 for resources the caller may not know exist, but do it on purpose.
- **Retrying non-idempotent calls** with no key.

## Trade-offs

<Callout kind="tradeoff">
Strict resource modelling gives a uniform, cacheable API but can fit awkwardly for actions and for reads that join many things. Pragmatic APIs mix both: resources for data, a few clearly named action endpoints for operations. What matters is that the exceptions are deliberate and documented.
</Callout>

## In production

<Callout kind="prod">
Require idempotency keys on every endpoint that moves money or creates external side effects, and store them with the result. Return `Location` on 201, and `Retry-After` on 429 and 503. Document each endpoint's status codes, since clients write code against them.
</Callout>
