## Why it exists

`GET /orders` on a table with ten million rows must not return ten million rows. An unbounded endpoint is slow, expensive and a ready-made denial of service. Every list needs a limit and a way to ask for the next part. And since the API will live longer than its first design, you also need a plan for changing it without breaking the code that already calls it.

<Callout kind="why">
Bounded lists protect your servers, and a versioning policy protects your clients. Both are promises that are far cheaper to make at the start than to add later.
</Callout>

## How it works

### Offset pagination

`?limit=20&offset=40` maps to `LIMIT 20 OFFSET 40`. It is easy to build and lets a client jump to page 7. It has two problems.

**Cost:** the database must walk past all 40 skipped rows to find the 41st. Page 50 000 does that walking every time.

**Consistency:** the data moves between requests. Take ten rows, read three, delete row 2, then read the next three with offset 3:

```js file=page.mjs mark=3,4,5
let rows = Array.from({ length: 10 }, (_, i) => ({ id: i + 1 }));
const offsetPage = (offset, limit) => rows.slice(offset, offset + limit).map(r => r.id);
const keysetPage = (after, limit) => rows.filter(r => r.id > after).slice(0, limit).map(r => r.id);
// page 1: offsetPage(0,3) -> [1,2,3]    keysetPage(0,3) -> [1,2,3]
rows = rows.filter(r => r.id !== 2);                 // a row is deleted between requests
// page 2: offsetPage(3,3) -> [5,6,7]    keysetPage(3,3) -> [4,5,6]
```

Offset page 2 returns `[5, 6, 7]`: row 4 shifted into the first page's range and was **never shown**. Keyset page 2 returns `[4, 5, 6]`, which is right.

### Cursor (keyset) pagination

Instead of "skip N", say "give me the rows after the last one I saw": `WHERE id > :last ORDER BY id LIMIT 20`. With an index on `id` the database jumps straight to that point, so page 50 000 costs the same as page 1, and inserts or deletes do not shift the window. The API returns an opaque **cursor** that the client sends back:

```js file=cursor.mjs mark=1
const cursor = Buffer.from(JSON.stringify({ id: 3 })).toString("base64url"); // "eyJpZCI6M30"
JSON.parse(Buffer.from(cursor, "base64url")); // { id: 3 }
```

Treat the cursor as opaque and **validate it on the way back in**: it is client input like any other (see the validation chapter), and encoding does not make it trustworthy. If you sort by something that is not unique (a timestamp), include a unique tie-breaker such as the id in both the sort and the cursor, otherwise rows with equal values are skipped or repeated.

The cost: no jumping to "page 7", and a stable sort key is required.

### Filtering and sorting

Accept filters as named query parameters (`?status=open&created_after=2026-01-01`) and sorting as an allow-listed field (`?sort=-created_at`). Never pass a client-supplied column name or `ORDER BY` fragment into SQL; map it from a fixed list instead. Always cap `limit` and apply a sensible default.

### Versioning

A **breaking change** is one that makes a correct existing client fail: removing or renaming a field, changing a type or meaning, tightening validation, or adding a required input. Adding optional fields and new endpoints is not breaking, *provided* clients ignore fields they do not know.

Common ways to carry a version: in the path (`/v2/orders`), in a header, or by date (a client pins "the API as of 2026-03-01"). Path versioning is the easiest to see, test and cache. Whatever you choose:

- Prefer **additive evolution** and keep one version alive as long as possible.
- Announce deprecation with a date, a `Deprecation` or `Sunset` header, and usage metrics per client.
- Never change the meaning of an existing field in place.

## Common mistakes

<Callout kind="mistake">
Paginating without a stable, unique sort order. Without it, two requests can disagree about which row comes next, so items repeat or vanish even with cursors.
</Callout>

- **No maximum `limit`**, so `?limit=1000000` works.
- **Returning total counts on huge tables** with `COUNT(*)` on every page; it can cost more than the page itself.
- **Passing user input into `ORDER BY`** or column names.
- **Versioning everything at once**, forcing clients to migrate for one changed endpoint.

## Trade-offs

<Callout kind="tradeoff">
Offset pagination suits small, slow-changing data and admin screens where jumping to a page matters. Cursor pagination suits feeds, large tables and anything under constant writes, at the price of no random page access. Many APIs offer cursors by default and keep offset only where a UI truly needs page numbers.
</Callout>

## In production

<Callout kind="prod">
Default and cap `limit`, index the columns you filter and sort on, and make cursors opaque and signed or validated. Track which clients call which version so a deprecation is a measured decision, not a guess. Contract tests that compare responses against the published schema catch accidental breaking changes before they ship.
</Callout>
