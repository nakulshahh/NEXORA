## Why it exists

Chat is the standard case for persistent connections, ordering and routing, building on the WebSocket lesson (D6).

<Callout kind="why">
Users judge it by feel: instant delivery, no lost or duplicated messages, correct order.
</Callout>

## How it works

1. **Connect**: clients hold a WebSocket to a gateway server (fall back to long polling where blocked). Gateways are stateful, each holding thousands of connections.
2. **Send**: the client sends a message with a client-generated id. The server authorises it, assigns the conversation's next **sequence number** (a counter per conversation, in the database), **persists** it, then acknowledges the sender.
3. **Fan out**: look up the conversation's members and which gateway each is connected to (a presence map in a shared store), then publish to those gateways via pub/sub; each pushes to its sockets.
4. **Offline users**: they are not connected, so the stored message waits. On reconnect the client says "my last sequence number is 120" and the server replays everything after it, which also repairs any gap. Optionally trigger a push notification (F4).
5. **Duplicates**: the client retries unacknowledged sends; the server de-duplicates by client message id.

Ordering is per conversation, not global; a single sequencer per conversation (one writer) is simple and enough. For very large groups, fan-out cost grows with members (see F7); read receipts and typing indicators are ephemeral and need not be stored.

Backpressure: a slow client cannot keep up; bound its outbound buffer and drop or disconnect it.

## Common mistakes

<Callout kind="mistake">
Delivering to online users first and storing later. A crash between the two loses a message the sender thinks was sent.
</Callout>

- **Ordering by client timestamps.**
- **No replay after reconnect.**
- **Unbounded per-connection buffers.**
- **Sticky load balancing assumed without a presence map.**

## Trade-offs

<Callout kind="tradeoff">
Persist-then-deliver adds a write to the latency path and guarantees durability. Skipping storage lowers latency and loses messages on failure.
</Callout>

## In production

<Callout kind="prod">
Monitor connection counts, delivery latency, reconnect rates and queue lag; roll out gateways with graceful drain (C2) so deploys do not drop everyone at once.
</Callout>
