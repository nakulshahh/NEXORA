## Why it exists

"There are only two hard things in computer science: cache invalidation and naming things." The joke lasts because correctness depends on *when* a cached copy stops being allowed to answer. And caches create a failure mode that did not exist before: the load of a hot key's expiry.

<Callout kind="why">
Every cache is a copy. Copies diverge. Your job is to decide how far they may drift, and what happens at the instant a popular copy disappears.
</Callout>

## How it works

### Write strategies

- **Cache-aside with delete-on-write**: update the database, delete the key. The next read refills it. Simple, and the usual default.
- **Write-through**: write to cache and database together. Reads are always warm, writes cost more, and the two writes can still fail separately.
- **Write-behind**: write to the cache and flush to the database later. Fast, but a crash can lose data. Rarely the right answer.

### The invalidation race

1. Reader misses, reads the old row from the database.
2. Writer updates the row and deletes the cache key.
3. Reader stores the old row in the cache.

Now the cache holds stale data and nothing will clear it until the TTL. This is why every cached entry should have a TTL, even when you also invalidate, and why correctness-critical reads (checking a balance before a payment) should go to the database.

### Stampede

A popular key expires. In a test with 100 concurrent requests arriving while the key was missing, and a database call taking 50 ms:

```text file=stampede.txt
naive cache-aside:        100 concurrent misses -> 100 database calls
single-flight:            100 concurrent misses ->   1 database call
```

**Single-flight** (also called request coalescing) lets the first miss do the work and makes the others await the same promise:

```ts file=single-flight.ts mark=3,4,5
const inflight = new Map<string, Promise<unknown>>();
function load(key: string, fetch: () => Promise<unknown>) {
  if (!inflight.has(key))
    inflight.set(key, fetch().finally(() => inflight.delete(key)));
  return inflight.get(key)!;
}
```

This works within one process. Across many instances use a short Redis lock (`SET key lock NX PX 5000`) or serve **stale-while-revalidate**: return the expired value immediately while one request refreshes it in the background.

### Jitter

If a thousand keys are all cached with a 60-second TTL at startup, they all expire together. Add random jitter to each TTL (for example 60 s plus or minus 10 percent) so expiries spread out.

### When not to cache

Skip caching data that changes constantly, is rarely re-read, must be exactly correct (balances, inventory at checkout), or is cheap to compute. First fix the slow query with an index; a cache that hides a missing index only postpones the problem.

## Common mistakes

<Callout kind="mistake">
Relying on invalidation alone with no TTL. One missed delete in an error path and the wrong value lives forever.
</Callout>

- **Many keys with identical TTLs** that expire in a burst.
- **Cold-start outages**: a deploy empties the cache and the database takes the full load. Warm it or ramp traffic.
- **Caching a failure** (a timeout stored as "not found").
- **Caching authorization-sensitive responses** without the user in the key.
- **Using the cache as a lock or queue** without understanding its failure modes.

## Trade-offs

<Callout kind="tradeoff">
Single-flight and locks protect the database but add latency for waiters and failure cases (what if the winner crashes?). Stale-while-revalidate gives smooth latency at the cost of briefly serving old data. Pick based on how stale each endpoint may be.
</Callout>

## In production

<Callout kind="prod">
Alert on a hit-rate drop and on database load spikes that follow cache restarts. Put a short timeout on cache calls and fall back to the database, so a slow cache does not become an outage. Rehearse a cold cache in load tests.
</Callout>
