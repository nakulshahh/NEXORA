## Why it exists

Once a feature calls a model, it inherits a new cost line, a new latency profile and a new class of security problems. Engineering it well looks like engineering any expensive, flaky dependency (B9), plus the problem that its output is text that someone may treat as trusted.

<Callout kind="why">
Design as if the model will sometimes be slow, wrong or manipulated, because it will be, and decide what the system does then.
</Callout>

## How it works

### Cost and latency from first principles

Cost is roughly (input tokens x input price + output tokens x output price) x requests. Do the arithmetic before building, with the current prices from your provider's page (they change, so keep them in configuration, not in your head). A worked shape with illustrative round numbers: if a request sends 3 000 input and 500 output tokens, and a million-token input price is *P_in* and output price *P_out*, then 100 000 requests per day cost 100 000 x (3 000 x P_in + 500 x P_out) / 1 000 000. The structure matters: **input tokens dominate when you stuff retrieved passages and history into every call**, so cutting context cuts cost and latency together.

Latency is mostly output length: tokens are generated one after another, so a long answer takes proportionally long. Use **streaming** so users see text immediately, set a hard **timeout**, and keep outputs short where you can (ask for structured, concise results).

### Reducing both

- **Cache** identical requests (same input, deterministic settings) and use provider **prompt caching** for the large stable prefix (instructions, documents).
- **Retrieve less, better**: send the top few relevant passages, not everything.
- **Route by difficulty**: a small, cheap model for classification or extraction, a larger one only when needed.
- **Batch** offline work; accept asynchronous latency for non-interactive jobs.
- **Rate-limit and budget** per user and per day, so one user or a loop cannot spend the month's money (C3).

### Treat output as untrusted

Never execute, render as HTML, interpolate into SQL or follow links from model output without the same handling as any user input. Ask for **structured output** (a JSON Schema) and **validate** it with your schema library (A5); on failure retry once or fall back. Constrain actions to an allow-list of operations. Filter or label content when the domain requires it, and cite sources so users can check.

### Prompt injection

**Prompt injection** is when text the model reads (a user message, a web page, a document, an email) contains instructions that the model follows instead of yours. It cannot be fully prevented by wording. Layered defence:

1. **Least privilege**: the model's tools can do only what the current user may do, enforced in code.
2. **Separate trust levels**: mark retrieved or user-provided text as data, and never let it choose tools or targets by itself.
3. **Confirm consequential actions** with the user or a human (sending, paying, deleting).
4. **Output checks**: block responses that leak secrets or system text; scan for exfiltration patterns such as links containing data.
5. **Monitor and red-team**: log attempts, and keep a test set of injection attacks that runs in CI.

### Fallbacks and people

When the model is down, slow or over budget, degrade: cached answers, a simpler path, a message that says the feature is unavailable. For decisions that affect people (credit, hiring, moderation) keep a human accountable and provide a way to contest. Do not log sensitive prompts carelessly; they contain user data.

## Common mistakes

<Callout kind="mistake">
Sending the entire conversation and all retrieved text on every turn "to be safe". Cost and latency balloon, and irrelevant context can make answers worse.
</Callout>

- **No timeout or budget**, so one stuck call or loop is expensive.
- **Rendering model output as HTML** without sanitising.
- **Giving the model broad credentials.**
- **Logging full prompts with personal data.**
- **Changing the model or prompt without re-running evaluations.**

## Trade-offs

<Callout kind="tradeoff">
Larger models are more capable and slower and costlier. Caching and shorter contexts save money and add staleness and engineering. Strong guardrails reduce harm and false refusals annoy users; tune them with measured examples, not instinct.
</Callout>

## In production

<Callout kind="prod">
Track tokens, cost, latency percentiles, error and refusal rates per feature and per user tier; alert on budget burn; keep prompts and models versioned with an evaluation run per change; and rehearse the provider being down.
</Callout>
