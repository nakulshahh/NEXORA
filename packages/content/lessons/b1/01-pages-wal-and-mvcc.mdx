## Why it exists

Disks and SSDs do not hand you one byte at a time; they move blocks. Memory is faster than disk by orders of magnitude, and power can fail at any instant. A database has to be fast *and* never lose a transaction it said was committed. Pages, a log and row versioning are the three ideas that make that possible.

<Callout kind="why">
Almost every performance property you will study later (why scans are slow, why indexes help, why writes cost more than reads) follows from "data lives in pages, and the log is written first".
</Callout>

## How it works

### Tables are heaps of pages

A table is stored as a **heap**: a file divided into fixed-size **pages** (8192 bytes in PostgreSQL, checked with `SHOW block_size`). Each page holds many row versions, called **tuples**. You can see where a row lives with the hidden `ctid` column, which is *(page number, slot within the page)*. On the lab table in this chapter's examples (one million rows of about 170 bytes):

```sql file=ctid.sql mark=1
SELECT id, ctid FROM users WHERE id IN (1, 2, 100, 150000);
--  1 → (0,1)    2 → (0,2)    100 → (2,6)    150000 → (3323,40)
```

The whole table occupied 22 213 pages, about 174 MB. A query that must examine every row (a **sequential scan**) reads all of those pages. That number, not the row count alone, is the cost.

### Write-ahead logging

Changing a page in memory and writing it back later is fast but unsafe: lose power in between and the change is gone. Writing every changed page to disk at commit would be safe but slow and scattered.

The compromise is the **write-ahead log (WAL)**: before a change is applied to data pages, a compact description of it is appended to a sequential log file. **Commit returns only after the log record is flushed to durable storage** (`fsync`). Data pages themselves can be written later, in the background. After a crash the database replays the log and recovers every committed change.

Sequential appends are far cheaper than scattered page writes, so this gives durability at a small cost. You can watch the log grow:

```sql file=wal.sql mark=1,3
SELECT pg_current_wal_lsn();            -- a position in the log
INSERT INTO users(email, country, bio) VALUES ('wal@example.com', 'IN', 'x');
SELECT pg_current_wal_lsn();            -- advanced by the size of the log record
```

On the lab table, which had six indexes, one single-row insert advanced the log by 33 240 bytes. That is much larger than the row itself because the log also describes the index changes, and the first modification of a page after a checkpoint logs the whole page. It is a measurement from one run, not a constant. The same log is what **replication** ships to replicas, which a later chapter builds on.

### Row versions

An `UPDATE` does not edit the old tuple. It writes a new tuple (possibly on another page) and marks the old one as no longer current:

```sql file=update.sql mark=1,2
UPDATE users SET bio = 'y' WHERE id = 1;
SELECT id, ctid FROM users WHERE id = 1;   -- was (0,1), now (0,48): a new version
```

This is **multi-version concurrency control (MVCC)**: each transaction sees the versions that were current when it started, so a reader does not wait for a writer. The price is **dead tuples**: old versions that nothing can see any more. **Vacuum** removes them and marks the space reusable; without it tables bloat and scans read pages full of garbage. The transactions chapter shows how MVCC produces the isolation levels.

## Common mistakes

<Callout kind="mistake">
Thinking `DELETE` or `UPDATE` immediately frees disk space. The old versions stay until vacuum runs, and the file does not shrink; the space is reused for future rows.
</Callout>

- **Assuming a committed write is already in the data file.** It is durable because of the log, not because the page was written.
- **Disabling `fsync` or relying on a cache that lies** for speed, which turns a crash into silent data loss.
- **Ignoring table bloat** on tables with heavy updates, then wondering why queries slow down.
- **Estimating cost by row count** instead of page count and access pattern.

## Trade-offs

<Callout kind="tradeoff">
Write-ahead logging makes every write do the work twice (log, then data page) and makes commit latency depend on the disk's flush time. In return you get crash safety and fast sequential I/O. MVCC removes read/write blocking but needs vacuum and extra space. Systems that tune these away (asynchronous commit, in-memory stores) get speed by accepting that a crash can lose recent data.
</Callout>

## In production

<Callout kind="prod">
Watch commit latency and disk flush time, keep autovacuum healthy and monitor dead-tuple counts and table size, and take base backups plus archived WAL so you can restore to a point in time. Treat "the disk reports success" as a requirement: use storage whose flush semantics you trust.
</Callout>
