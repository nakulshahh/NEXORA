## Why it exists

Your app talks to the database over a **connection**: an authenticated session with its own state and, in PostgreSQL, its own server process using memory. Creating one takes several network round trips (TCP, TLS, authentication, session setup). Doing that for every request adds latency and wastes work; and the database only allows a limited number at once (`max_connections` defaults to 100 in PostgreSQL).

<Callout kind="why">
A pool pays the connection cost once and turns "unlimited concurrent requests" into "a bounded number of concurrent queries plus a queue", which is something a database can survive.
</Callout>

## How it works

A pool owns up to `max` open connections. A request **borrows** one, runs its queries, and **returns** it. If none is free, the request waits in a queue until one is returned (or a timeout fires).

Measured on a local PostgreSQL 16 with no TLS (so the real network cost is higher):

```js file=pool.mjs mark=3,8,9
// opening, querying and closing a fresh connection each time, averaged over 200 runs
//   4.40 ms per query
// reusing one open connection, same query
//   0.075 ms per query
```

Even with zero network distance, a fresh connection cost about 60 times more than reusing one. Across a real network with TLS the gap is larger.

### The queue

Take a pool of `max: 2` and six concurrent queries that each take 100 ms:

```js file=queue.mjs mark=1,2
const pool = new pg.Pool({ connectionString, max: 2 });
await Promise.all(Array.from({ length: 6 }, () => pool.query("select pg_sleep(0.1)")));
```

The queries finished at about 105, 105, 207, 207, 309 and 309 ms: two at a time, three waves. That is the pool doing its job: the database never ran more than two at once, and the other four waited their turn instead of piling on.

### The hard limit

Opening plain connections in a loop on the same server, the 101st was refused with `sorry, too many clients already`. With several app instances each holding a pool, `instances × pool size` must stay under the database's limit, with room left for admin tools and migrations.

### Sizing

Start small. A common starting point is a pool of roughly the database's core count times a small factor (for example 2 to 4 times), then measure. Throughput usually rises and then flattens or falls as connections increase. If many instances need many connections, put an external pooler (such as PgBouncer) in front, which multiplexes thousands of client connections onto a few server connections. Note that session-level features (prepared statements, `SET`, advisory locks) can behave differently through a pooler in transaction mode.

## Common mistakes

<Callout kind="mistake">
Borrowing a connection and not returning it on an error path. Each leak shrinks the pool by one until every request waits forever. Always release in a `finally` block, or use helpers that do it for you.
</Callout>

- **Holding a connection while doing slow non-database work** (calling another API, waiting on a user).
- **Pool size times instances above the database limit**, which causes errors only at scale-out time.
- **No acquisition timeout**, so requests queue indefinitely instead of failing fast.
- **Transactions left open**, which pin a connection and can block vacuum.

## Trade-offs

<Callout kind="tradeoff">
A small pool protects the database but makes requests queue during spikes, which shows up as latency. A large pool hides short spikes but can push the database into thrashing. You are choosing where the waiting happens: in your application's queue, where you can time out and shed load, or inside the database, where you cannot.
</Callout>

## In production

<Callout kind="prod">
Export pool metrics (in use, idle, waiting) and alert on the waiting count, set a short acquire timeout, cap pool size per instance, and account for autoscaling in the total. Use a managed or external pooler when instance counts are large or short-lived (serverless functions especially).
</Callout>
