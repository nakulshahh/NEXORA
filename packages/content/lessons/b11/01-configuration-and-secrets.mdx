## Why it exists

The same build should run in your laptop, staging and production, behaving differently only because of **configuration**: database URL, ports, origins, feature switches, keys. Mixing these into code means rebuilding per environment and leaking secrets into version control, the most common way credentials escape.

<Callout kind="why">
Code answers "what does the program do". Configuration answers "where and with what does it run". Keeping them apart lets one tested artifact move through environments unchanged.
</Callout>

## How it works

### Read once, validate at startup

Read configuration from environment variables in a single module, validate types and ranges, and refuse to start on a bad value. A real example from this project's API (`apps/api/src/config.ts`) parses everything through a schema:

```ts file=config.ts mark=3,4,5
const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535).default(4000),
  DATABASE_URL: z.string().min(1),
  COOKIE_SECRET: z.string().min(32),
});
// invalid -> throws "Invalid environment:\n  COOKIE_SECRET: ..." and the process exits
```

Failing at boot with a precise message beats a mysterious error an hour later at 3 a.m. Note the coercion: environment variables are always strings, so numbers must be parsed (the A5 lesson on coercion applies).

### Defaults and layers

Give safe defaults for local development, require production-critical values explicitly, and make dangerous values hard to set by accident (a production deploy should not silently use a development secret). Keep an `.env.example` documenting every variable with fake values; real `.env` files stay out of version control.

### Secrets are different

A **secret** is configuration whose exposure causes harm: passwords, API keys, signing keys, tokens.

- **Never in code, images or logs.** Scan repositories and CI for leaks.
- **Separate per environment** so a leak of staging does not expose production.
- **Least privilege**: a key that can only do what the service needs.
- **Rotate** on a schedule and immediately on suspicion, which means the system must support changing a secret without a rebuild, and ideally two valid keys at once during rotation.
- **Prefer a secret manager** or the platform's encrypted secret store, injected at runtime, with an audit trail.

If a secret leaks: revoke and rotate first, then investigate where it was used, then clean up history. Deleting the commit is not the fix.

### Feature flags and drift

Feature flags are runtime configuration that turn behaviour on or off without a deploy; they let you ship code dark, ramp gradually and cut off a failing feature (the degrade-gracefully idea from fault tolerance). Treat them as debt: remove them when done. **Drift** is when environments diverge in undocumented ways, so "works in staging" means little. Define configuration declaratively, review changes like code, and keep staging structurally similar to production.

## Common mistakes

<Callout kind="mistake">
Committing a `.env` file "just for now". Public or private, a pushed secret must be treated as compromised and rotated.
</Callout>

- **Reading `process.env` scattered through the code**, so nothing validates it.
- **Defaults that quietly work in production** with dev credentials.
- **Logging the whole configuration object** at startup.
- **One shared secret across environments and services.**
- **No rotation path**, so after a leak a deploy of hours is needed.

## Trade-offs

<Callout kind="tradeoff">
Strict validation can block a boot over a typo, which is the point, but it needs good messages. Secret managers add a dependency and setup but give rotation and audit. Many feature flags give flexibility and a combinatorial test burden.
</Callout>

## In production

<Callout kind="prod">
Inject secrets at runtime from a managed store, restrict who can read them, enable secret scanning in CI and push protection on the repository, document a rotation runbook, and rehearse it once so it works under pressure.
</Callout>
