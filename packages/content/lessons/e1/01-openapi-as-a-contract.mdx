## Why it exists

A client developer needs to know exactly what to send and what comes back, including errors. Prose in a wiki goes stale; a machine-readable contract can be tested, versioned and turned into code.

<Callout kind="why">
The contract is the interface between teams. Making it a file that tools can read turns arguments about what the API does into a diff you can review.
</Callout>

## How it works

### Anatomy

An OpenAPI 3.1 document is JSON or YAML with a few top-level parts:

- `info` and `servers`: name, version, base URLs.
- `paths`: each URL with its **operations** (`get`, `post`, ...), their parameters, request body schema and a response per status code.
- `components`: reusable pieces: **schemas** (JSON Schema), security schemes, shared responses.
- `security`: which operations need which scheme (a cookie, a bearer token, an API key).

This project's API document (`apps/api/src/openapi.ts`, served at `/api/openapi.json`) describes 15 paths: health and readiness probes, the auth routes (register, login, logout, sessions, OAuth start and callback, account) and the progress routes. It declares a cookie security scheme and one shared `Error` schema, so every failure response has the same shape: `{ error: { code, message } }`.

### One source of truth

The same Zod schemas that validate requests at runtime are converted to JSON Schema for the document:

```ts file=openapi.ts mark=2,3
const Credentials = z.object({ email: z.email(), password: z.string().min(1).max(128) });
// the same schema validates the request and, converted, documents it:
Credentials: z.toJSONSchema(Credentials, { target: "draft-2020-12", io: "input" }),
```

Change a limit in the schema and the validation and the documentation change together. That is the pattern to aim for: **schema first**, with docs, types and validation derived. The alternative, **contract first**, writes the OpenAPI document by hand and generates server stubs and client types from it; it suits teams that agree on the interface before building, at the cost of keeping generation in the build.

### Why the error schema matters

A documented, consistent error shape (a stable `code` for programs and a `message` for people) is part of the contract. Clients branch on `code`, never on message text (A5). Document each status an operation can return: 200, 201, 400 or 422 for validation, 401, 403, 404, 409, 429.

### What tooling reads it

- **Docs UIs** (Swagger UI, Redoc, Scalar) render it interactively.
- **Client generators** produce typed SDKs in many languages.
- **Validators and mocks** check traffic against the contract or serve fake responses before the backend exists.
- **Contract tests** (next lesson) confirm the running server matches the document.

## Common mistakes

<Callout kind="mistake">
A document that lists only the happy path. Clients then discover errors, rate limits and auth rules in production. Describe failures as carefully as successes.
</Callout>

- **Hand-maintained specs** with no check against the server.
- **Different error shapes per endpoint.**
- **Leaking internals** (database field names, admin-only routes) into the public document.
- **No `operationId`s**, so generated clients have ugly method names.
- **Treating the version string as decoration** and never bumping it for breaking changes.

## Trade-offs

<Callout kind="tradeoff">
Schema-first generation keeps code and docs in sync with the least effort and ties the document's detail to what your schema library can express. Contract-first gives you design control and a review step before coding, and needs generation tooling and discipline to keep the implementation conforming.
</Callout>

## In production

<Callout kind="prod">
Publish the document from CI as a build artifact, serve it at a stable URL, version it with the API, and keep internal and public documents separate so private routes are not advertised.
</Callout>
