## Why it exists

Limits protect capacity and fairness (C3). On one instance it is a map; across many it is a shared-state problem.

<Callout kind="why">
It is a small, sharp example of atomicity, shared state and failure policy.
</Callout>

## How it works

### Algorithms

- **Fixed window**: counter per client per time bucket. Cheap; bursts at the boundary (200 allowed in a short span in the measured run).
- **Sliding window log**: store timestamps; exact (100 allowed); memory grows with the limit.
- **Sliding window counter**: weight the previous and current window; approximate, small.
- **Token bucket**: tokens refill at a rate up to a capacity; each request spends one. Allows controlled bursts, steady rate. The usual choice.

### Sharing state

Every instance must read-modify-write the same counter atomically, or two instances both see 99 and both allow. Options: a database row updated with `UPDATE ... SET count = count + 1 ... RETURNING` (atomic, uses what you already run), or Redis `INCR` with expiry (fast, extra infrastructure). This project's design choice is Postgres-backed state so no new service is needed; a test runs two app instances against one database and checks the limit is shared.

### Failure policy

If the limiter store is down: **fail-open** (allow, risking overload) or **fail-closed** (reject, risking an outage caused by the limiter). Public APIs usually fail open for general limits and closed for security-critical ones such as login attempts.

### Responses

Return 429 with `Retry-After`, and consider `RateLimit` headers so clients can back off (B7, B9). Key by user or API key where possible; IP alone penalises shared networks.

## Common mistakes

<Callout kind="mistake">
Read-then-write in two statements. Concurrent requests both pass the check.
</Callout>

- **Trusting a spoofable forwarded IP header.**
- **No expiry on counters**, so storage grows.
- **One global limit** with no per-route or per-tier limits.
- **Not telling clients when to retry.**

## Trade-offs

<Callout kind="tradeoff">
Exact algorithms cost memory or round trips; approximate ones are cheap and slightly lenient. A shared store adds latency and a dependency; local limits are fast and imprecise.
</Callout>

## In production

<Callout kind="prod">
Track allowed versus rejected per route, alert on spikes, and test the store-down behaviour deliberately.
</Callout>
