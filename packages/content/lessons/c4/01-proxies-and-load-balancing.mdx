## Why it exists

One server has a capacity ceiling and is a single point of failure. Running several identical copies fixes both, but clients need one address and something must decide which copy handles each request. That something is a **reverse proxy** or **load balancer**.

<Callout kind="why">
Load balancing turns "can this machine cope" into "how many machines do we add", provided your servers are stateless enough to be interchangeable.
</Callout>

## How it works

A reverse proxy accepts client connections and forwards requests to **upstream** servers. Typical jobs: terminate TLS once, route by host or path, compress, cache static responses, enforce limits, add request ids, and hide the internal topology. It adds a hop (a little latency) and becomes critical infrastructure itself, so it is usually run redundantly.

### Choosing a server

Take three servers and 300 requests arriving every 15 ms. Most take 10 ms; about 5 percent take 400 ms (a heavy report, say). A seeded simulation of two policies:

| Policy | Mean latency | Worst latency |
| --- | --- | --- |
| Round robin | about 163 ms | about 975 ms |
| Least connections | about 51 ms | about 510 ms |

Round robin sent requests to a server that was busy with a slow one while another sat idle. Least connections looked at what each server was doing right now. This is a simplified model (no network, perfect knowledge of load), so trust the *direction*, not the figures. Other policies: random with two choices ("power of two choices" gives most of the benefit cheaply), weighted (unequal servers), and IP-hash or cookie-based (stickiness).

### Health checks and draining

The balancer probes each server (for example `GET /healthz`) and stops sending traffic to those that fail. Keep the health endpoint cheap and honest, and do not make it depend on the database or one DB outage removes every server at once. When deploying, **drain**: stop new requests to a server, let in-flight ones finish, then stop it.

### Sticky sessions versus stateless servers

Sticky routing pins a client to one server so in-memory sessions work. It is a patch: load becomes uneven, and when that server dies the sessions die with it. Better: keep session state in a shared store (database or Redis) or in a signed token, so any server can handle any request.

### Layers

An **L4** balancer routes TCP connections without reading HTTP: very fast, less flexible. An **L7** balancer parses HTTP, so it can route by path, header or cookie. A **CDN** is a geographically distributed set of caching reverse proxies for static and cacheable content, cutting latency by serving from near the user.

## Common mistakes

<Callout kind="mistake">
Putting per-user state in server memory and then adding sticky sessions "to make it work". It hides the design problem and turns every deploy into a mass logout.
</Callout>

- **No health checks**, so a dead server keeps receiving a share of traffic.
- **Health checks that depend on every downstream service**, causing cascading removals.
- **Forgetting that the real client IP is in a forwarded header**, breaking logs and rate limits.
- **A single proxy instance**, which is just a new single point of failure.
- **Scaling the web tier while the single database stays the bottleneck.**

## Trade-offs

<Callout kind="tradeoff">
A proxy tier adds a hop, configuration and a component to secure and monitor; in return it gives redundancy, zero-downtime deploys and a place for cross-cutting rules. Smarter balancing needs more state (connection counts) and can still make mistakes when load information is stale.
</Callout>

## In production

<Callout kind="prod">
Run at least two balancer instances, forward and trust client-IP headers only from your own proxies, set sensible timeouts and retry rules (retry only idempotent requests), watch per-server latency and error rates, and test taking one server away under load.
</Callout>
