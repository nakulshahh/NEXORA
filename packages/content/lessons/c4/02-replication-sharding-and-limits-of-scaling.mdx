## Why it exists

Caches and indexes stretch one database a long way, but eventually reads outnumber what one machine can serve, availability demands a standby, or the data simply no longer fits. There are two basic moves: **copy** the data, or **split** it.

<Callout kind="why">
Scaling data is harder than scaling stateless servers because data has to stay correct. Each technique trades some simplicity or consistency for capacity.
</Callout>

## How it works

### Replication

One **primary** accepts writes and streams its write-ahead log (from the first chapter of this part) to one or more **replicas**, which apply it and can serve read-only queries. Benefits: read capacity grows with replicas, a replica can be **promoted** if the primary fails, and backups or analytics can run on a replica.

Costs: with asynchronous replication a replica lags the primary, by milliseconds normally and far more under load. Consequences to design for:

- **Read-your-writes**: after a user saves something, read that user's data from the primary for a short while, or pass a position token.
- **Stale reads** are acceptable for feeds and dashboards, not for balance checks.
- **Failover** can lose the last few transactions if replication was asynchronous, and needs a mechanism to prevent two primaries ("split brain").

Replication does not increase write capacity: every write still goes to one primary.

### Sharding

To scale writes and size, split rows across servers by a **shard key** (for example the user id). Each shard owns a slice. Costs: queries that cross shards are slow or impossible, joins and transactions across shards are hard, and resharding is painful. A poor key creates a **hot shard** (one celebrity user, or time-based keys sending all new writes to one shard).

### Which shard owns a key?

Simplest: `shard = hash(key) mod N`. The problem is changing N. Moving from 4 to 5 servers with 10 000 keys:

```text file=remap.txt
modulo hashing:                80.3% of keys moved
consistent hashing (100 vnodes): 20.9% of keys moved   (ideal: 20%, i.e. 1/5)
```

**Consistent hashing** places servers (many virtual points each) on a ring and assigns each key to the next server clockwise, so adding a server takes keys from its neighbours only. It is used by caches and distributed stores because rebalancing moves a minimum of data.

### The limits: Amdahl's law

If a fraction `p` of the work can run in parallel, the speedup on `n` machines is `1 / ((1 - p) + p / n)`. At `n = 8`: p = 0.5 gives 1.78x, p = 0.9 gives 4.71x, p = 0.95 gives 5.93x. As `n` grows without bound, the speedup tops out at `1 / (1 - p)`: 2x, 10x, 20x. The serial part (a global lock, one coordinator, the primary database) caps everything. This is why finding and shrinking the serial bottleneck beats adding machines, and why "scale out" is not a magic word.

## Common mistakes

<Callout kind="mistake">
Reading from a replica right after a write and showing the user stale data. Route a user's reads to the primary briefly after they write, or design the UI to tolerate lag.
</Callout>

- **Sharding too early**, taking on large complexity for a problem an index would solve.
- **Choosing a shard key with skew** (country, date) and creating hot shards.
- **Assuming replicas are backups.** A bad `DELETE` replicates instantly; keep real backups.
- **Mod-N hashing for a cache cluster**, so adding a node invalidates most of the cache.
- **Ignoring failover testing**: a promotion procedure that was never rehearsed fails when needed.

## Trade-offs

<Callout kind="tradeoff">
Vertical scaling (a bigger machine) is the simplest and has a ceiling. Replication adds read capacity and availability with lag. Sharding adds write and storage capacity with large complexity. Choose the lightest option that covers the measured need.
</Callout>

## In production

<Callout kind="prod">
Monitor replication lag and alert on it, rehearse failover, keep point-in-time backups independent of replicas, keep shard keys and routing logic in one place, and make resharding a planned, tested operation rather than an emergency.
</Callout>
