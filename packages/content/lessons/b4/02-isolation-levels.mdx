## Why it exists

Transactions running one after another are easy to reason about. Real systems run thousands at once, and running them truly one at a time would be too slow. **Isolation levels** are the dial between "safe like serial" and "fast with surprises".

<Callout kind="why">
Most concurrency bugs in web backends are not exotic. They are check-then-act code (read a value, decide, write) running in two requests at once.
</Callout>

## How it works

PostgreSQL uses MVCC: each statement or transaction sees a **snapshot** of committed data. The level determines *when* the snapshot is taken.

- **Read committed** (default): each statement sees what was committed when *it* started.
- **Repeatable read**: the whole transaction sees the snapshot from its first statement.
- **Serializable**: behaves as if transactions ran one at a time; the database aborts any that would break that illusion.

Everything below was run against PostgreSQL 16 with two sessions.

### Non-repeatable read

Session A reads a balance of 100. Session B commits a change to 200. Session A reads again:

```text file=nonrepeatable.txt
read committed:   100 -> 200   (the value changed inside one transaction)
repeatable read:  100 -> 100   (same snapshot all the way)
```

### Lost update

Both sessions read 100, both compute 110 and write. The final balance should be 120 but is:

```text file=lostupdate.txt
read committed:   final 110                       (one increment silently lost)
repeatable read:  final 110, and the second writer got
                  "could not serialize access due to concurrent update"
```

Under repeatable read the database noticed and refused, so you can retry. Under the default level it quietly lost data. Two fixes avoid the problem at any level:

```sql file=fixes.sql mark=1,4
UPDATE acct SET bal = bal + 10 WHERE id = 1;     -- atomic: final 120 in the test

BEGIN;
SELECT bal FROM acct WHERE id = 1 FOR UPDATE;    -- the second session waits here
UPDATE acct SET bal = ... WHERE id = 1;          -- final 120 in the test
COMMIT;
```

An atomic update lets the database do the arithmetic under a row lock. `FOR UPDATE` locks the row after reading it so competing writers queue.

### Write skew

Rule: at least one person must be on call. Alice and Bob are both on call. Each transaction checks "is more than one on call?", sees two, and takes themselves off. They touch *different rows*, so row locks do not conflict:

```text file=writeskew.txt
repeatable read:  both saw 2, both committed, on call afterwards: 0   (rule broken)
serializable:     both saw 2, one commit failed with
                  "could not serialize access due to read/write dependencies
                   among transactions", on call afterwards: 1
```

Only serializable detected the invalid combination. Alternatives are to lock the rows you read (`SELECT ... FOR UPDATE` on the on-call set) or to enforce the rule with a constraint where possible.

### Retrying

Serialization failures and deadlocks are normal at higher levels. The correct response is to **retry the whole transaction** from `BEGIN`, a bounded number of times with jitter, and only if its side effects are all inside the database.

## Common mistakes

<Callout kind="mistake">
Read-modify-write in application code under the default level: select the value, add in JavaScript, update. It works in tests and loses data under concurrency.
</Callout>

- **Believing "I used a transaction" means "I am safe".** Safety depends on the level and the access pattern.
- **Using serializable without retry logic**, so users see errors.
- **Retrying only the failed statement** rather than the whole transaction.
- **Locking rows in inconsistent order**, which causes deadlocks.
- **Enforcing uniqueness by check-then-insert** instead of a unique constraint.

## Trade-offs

<Callout kind="tradeoff">
Stronger isolation removes whole classes of bugs but increases aborts and coordination. Weaker isolation is cheaper but moves correctness into your code. A good default is read committed with atomic updates, unique constraints and targeted `FOR UPDATE`, using serializable for the few invariants that span several rows.
</Callout>

## In production

<Callout kind="prod">
Prefer database-enforced rules (unique, foreign key, check) over application checks, make updates atomic expressions where possible, count and alert on serialization failures and deadlocks, and test concurrency with two parallel sessions or a load tool, not just unit tests.
</Callout>
