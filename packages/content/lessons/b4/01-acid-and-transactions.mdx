## Why it exists

Moving money means two writes: subtract from one account, add to another. If the process dies between them, money vanishes. A **transaction** makes the pair indivisible: either both happen or neither does. The same idea protects any multi-step change, such as creating an order and decrementing stock.

<Callout kind="why">
ACID is a contract between you and the database: you describe the unit of work, and it promises the unit is never half-applied, even with crashes and concurrent users.
</Callout>

## How it works

```sql file=transfer.sql mark=1,2,3,4
BEGIN;
UPDATE acct SET bal = bal - 30 WHERE id = 1;
UPDATE acct SET bal = bal + 30 WHERE id = 2;
COMMIT;      -- or ROLLBACK; to undo both
```

The four guarantees:

- **Atomicity**: all statements apply, or none do. On error or `ROLLBACK`, the new row versions are simply never made visible.
- **Consistency**: a committed transaction leaves the database satisfying its constraints (keys, `CHECK`, foreign keys). The database enforces the declared rules; your *business* rules are consistent only if you declare them.
- **Isolation**: concurrent transactions do not see each other's half-finished work. How strongly is configurable; the next lesson covers the levels and what each allows.
- **Durability**: once `COMMIT` returns, the change survives a crash, because the log record was flushed first, as in the pages and WAL lesson.

### Mapping to mechanisms

| Guarantee | Mostly implemented by |
| --- | --- |
| Atomicity | Row versioning, so uncommitted versions stay invisible |
| Consistency | Constraints checked at write or commit time |
| Isolation | MVCC snapshots plus locks |
| Durability | Write-ahead log flushed at commit |

### In application code

```ts file=transfer.ts mark=2,4,8,9
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query("UPDATE acct SET bal = bal - $1 WHERE id = $2", [amount, from]);
  await client.query("UPDATE acct SET bal = bal + $1 WHERE id = $2", [amount, to]);
  await client.query("COMMIT");
} catch (e) {
  await client.query("ROLLBACK");
  throw e;
} finally {
  client.release();
}
```

All statements must use the *same* connection, since a transaction belongs to one session. That is why you borrow one client from the pool rather than calling `pool.query` for each statement.

### Savepoints and deadlocks

A **savepoint** lets you undo part of a transaction without abandoning it. A **deadlock** happens when two transactions each wait for a lock the other holds; PostgreSQL detects it and aborts one with an error. The standard defence is to always touch rows in the same order (for example, lowest account id first).

## Common mistakes

<Callout kind="mistake">
Calling `pool.query` for each statement of a "transaction". Each call may use a different connection, so there is no transaction at all, and the BEGIN and COMMIT land on different sessions.
</Callout>

- **Doing slow work inside a transaction** (HTTP calls, user input), which holds locks and a connection.
- **Never releasing the client** after an error path.
- **Ignoring the abort state** after a failed statement.
- **Retrying a non-idempotent side effect** (an email, a payment call) inside a transaction that can be re-run.
- **Assuming consistency** without declaring the constraints that define it.

## Trade-offs

<Callout kind="tradeoff">
Longer transactions give wider guarantees but hold locks longer, reduce concurrency and bloat versions. Shorter transactions are faster and gentler but force you to design for partial progress. Keep the transaction as small as correctness allows, and make external side effects happen after commit.
</Callout>

## In production

<Callout kind="prod">
Set statement and idle-in-transaction timeouts, log and alert on deadlocks and serialization failures, and retry the whole transaction (not just the failed statement) when the database reports a retryable conflict. Keep outbound calls outside the transaction, using patterns such as an outbox table.
</Callout>
