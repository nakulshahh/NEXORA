## Why it exists

Once search lives in its own engine, there are two copies of every searchable record. They will disagree: a deploy kills a worker, the engine is down for a minute, a bug skips one event type. A search that shows deleted items or misses new ones erodes trust quickly.

<Callout kind="why">
Derived data needs a one-way flow from the source of truth plus a way to regenerate it from scratch. If you can always rebuild, drift is an inconvenience, not a disaster.
</Callout>

## How it works

### Three ways to feed the index

1. **Dual write**: the request handler writes the database and then the search engine. Simple and wrong: a failure between the writes leaves them inconsistent with no record of what to repair.
2. **Transactional outbox**: in the *same database transaction* as the change, insert an "index this record" row. A worker (B7) reads the outbox and updates the engine, retrying on failure. The change and the intent to index commit together or not at all.
3. **Periodic or on-demand reindex**: a job rebuilds the index from the database. Slow for large data, but the ultimate safety net.

Many systems combine 2 and 3: the outbox gives freshness, a nightly reindex corrects any drift. Larger systems use change data capture (reading the database's log, the same WAL from the first B-chapter) to feed indexes without application changes.

### Idempotent indexing

Indexing "upsert document id 42 with this content" is naturally idempotent: doing it twice is harmless, which fits at-least-once delivery. Deleting an already-deleted document must not fail. Include a version (an `updated_at` or a counter) so a late, older event cannot overwrite a newer one.

```sql file=outbox.sql mark=3,4
BEGIN;
UPDATE products SET name = $1 WHERE id = $2;
INSERT INTO search_outbox(entity, entity_id, op) VALUES ('product', $2, 'upsert');
COMMIT;   -- both happen, or neither
```

### Living with a delay

Seconds of lag are normal. Design the UI so it does not break: after a user creates an item, show it from the database response rather than expecting search to find it immediately; do not rely on search results for correctness (permissions must be enforced on the actual records, since an index can lag a revoked permission); and watch **lag** (age of the oldest unprocessed outbox row) as the health metric.

### Rebuilding safely

Reindex into a *new* index, then switch an alias or pointer to it once complete, so users never see a half-built index. Keep the old one briefly in case you need to roll back.

## Common mistakes

<Callout kind="mistake">
Trusting the search index for authorization. A document a user lost access to can remain searchable until the index catches up. Filter results against the source of truth, or include permission data and update it with priority.
</Callout>

- **Dual writes** with no repair job.
- **No lag metric**, so a stalled worker goes unnoticed for days.
- **Non-idempotent index updates**, so retries duplicate documents.
- **Reindexing in place**, exposing partial results.
- **Indexing sensitive fields** that should never be searchable.

## Trade-offs

<Callout kind="tradeoff">
An outbox adds a table and a worker but gives reliable, retryable propagation. Dual writes are simpler until the first failure. Full reindexing is robust and slow; incremental updates are fast and need careful handling of ordering and deletes.
</Callout>

## In production

<Callout kind="prod">
Alert on outbox age and on the count of failed index operations, run a scheduled reconciliation that compares counts or checksums between the database and the index, keep reindex runnable on demand, and test by killing the worker mid-stream.
</Callout>
