## Why it exists

Relational databases are general-purpose and strongly consistent, which is the right default (the B-chapters so far). But some workloads have a dominant access pattern or scale that a specialised store handles more simply: looking up a session by id at huge volume, storing nested documents read as a unit, or traversing relationships. "NoSQL" is a label for several different tools, not one technology.

<Callout kind="why">
Pick the data store from how you will read and write the data, then check what it costs to operate and what consistency it gives. Fashion is not a requirement.
</Callout>

## How it works

### The families

- **Key-value** (Redis, DynamoDB used simply): get and set by key. Extremely fast and easy to scale; no queries beyond the key. Good for sessions, caches, counters.
- **Document** (MongoDB, Postgres JSONB): nested JSON-like records read and written as a unit. Good when the entity is naturally a tree and mostly accessed whole.
- **Wide-column** (Cassandra, Bigtable): rows partitioned by a key, with very high write throughput and queries that follow the partition design. Good for time series and event logs at scale.
- **Graph** (Neo4j): nodes and edges with fast traversal. Good for "friends of friends" and recommendation paths where joins would explode.

### Postgres can be a document store

Postgres stores JSON as `jsonb` and can index it. On 300 000 events with a `data jsonb` column, finding events where `data @> '{"type":"buy","user":42}'`:

```text file=jsonb.txt
no index:                Seq Scan, 299 940 rows filtered,  about 51 ms
GIN index (jsonb_path_ops): Bitmap index scan,             about 0.45 ms
```

The table was 31 MB and the GIN index about 3 MB. So if you need flexible attributes next to transactional data, `jsonb` plus a GIN index often removes the reason for a second database. You keep transactions, joins and one backup story.

### What the schema looks like without a schema

Nothing stops a writer from sending the wrong type:

```sql file=drift.sql mark=1,2
INSERT INTO ev(data) VALUES ('{"type":"click","user":"forty-two"}');   -- user is a string here, a number everywhere else
SELECT count(*) FROM ev WHERE jsonb_typeof(data->'user') = 'string';   -- 1
```

The insert succeeded. A report that adds up `user` ids now breaks on one row. With a document store, enforce shape in application validation (the A5 techniques), version your documents, and migrate old ones deliberately. Where the structure matters (money, inventory), keep those columns relational and put only the variable part in JSON.

### Consistency and joins

Many NoSQL stores trade strong consistency, multi-row transactions or joins for scale and availability. That is a good deal when you can model around it (denormalise, one document per access pattern) and a bad one when your domain is relational. Design for the queries first: in a key-value or wide-column store the table layout *is* the query plan, and a new query shape can mean a new table or a migration.

## Common mistakes

<Callout kind="mistake">
Choosing a document store because the schema "might change", then discovering you need joins and transactions across collections. Relational databases handle schema change fine with migrations (B2).
</Callout>

- **Using two databases when one would do**, doubling operations and consistency problems.
- **Modelling documents like tables** and performing application-side joins.
- **Unbounded arrays inside documents** that grow until they hit size limits.
- **Ignoring consistency settings** and assuming a read sees the last write.
- **Picking by benchmark headlines** instead of your own access pattern.

## Trade-offs

<Callout kind="tradeoff">
A specialised store can be simpler and faster for one pattern and loses the generality, joins and transactions of SQL. Every additional data store adds operations, backups, failure modes and a consistency boundary. The default should be Postgres, with an extra store added only when a measured need justifies it.
</Callout>

## In production

<Callout kind="prod">
Decide ownership of each dataset (one system is the source of truth, the others are derived and rebuildable), validate document shapes on write, version documents, monitor store-specific signals (partition hot spots, replica lag), and rehearse restoring each store.
</Callout>
