## Why it exists

Networks drop packets, services restart, and databases time out. A job that fails once will often succeed a moment later, so retrying is right. But retries are also a classic way to turn a small problem into an outage, and a way to charge a customer twice.

<Callout kind="why">
Retries multiply load exactly when a system is weakest. They must be bounded, spread out in time and safe to repeat.
</Callout>

## How it works

### Exponential backoff

Wait longer after each failure. With a base of 100 ms and a factor of 2 the waits are:

```text file=backoff.txt
attempt 1: 100 ms   attempt 2: 200   attempt 3: 400   attempt 4: 800   attempt 5: 1600   attempt 6: 3200
```

Cap the delay (for example at 30 seconds) and the number of attempts.

### Jitter

If a thousand workers fail together and all wait exactly 200 ms, they all retry together, producing a **retry storm**: synchronized waves that hit the recovering service at the same instant. **Jitter** randomises each wait (a common choice is a uniform random delay between zero and the computed backoff), spreading the retries over time.

### Idempotency

An operation is **idempotent** if doing it twice has the same effect as once. Setting a value is; adding to a counter is not. Techniques:

- **Natural idempotency**: `UPDATE orders SET status = 'shipped' WHERE id = 7` is safe to repeat.
- **Uniqueness constraint**: record each processed event id in a table with a unique key; the second insert fails and you skip the work.
- **Idempotency key**: the client sends a unique key with the request; the server stores the key and the response and returns the stored response if the key repeats. (The REST chapter measured this pattern.)

```sql file=dedupe.sql mark=2,4
CREATE TABLE processed (event_id text PRIMARY KEY);
-- inside the job's transaction:
INSERT INTO processed(event_id) VALUES ($1) ON CONFLICT DO NOTHING;
-- if zero rows were inserted, this event was already handled: skip the side effect
```

Put the dedupe insert and the database effects in the *same transaction* so they commit together. For effects outside your database (email, third-party API), pass the key to the provider if it supports one, or accept at-least-once and make the effect harmless.

### Poison jobs and dead letters

Some jobs never succeed (bad payload, a bug). After a maximum number of attempts, move the job to a **dead-letter** state, keep its error, alert someone, and let operators replay it after a fix. Without this, one bad job can block or churn the queue forever.

### Know when to stop retrying

Retry transient errors (timeouts, 503) but not permanent ones (400, validation failure). When a dependency is clearly down, a **circuit breaker** stops calling it for a while and fails fast, so you do not waste capacity.

## Common mistakes

<Callout kind="mistake">
Retrying at every layer: the client retries three times, the gateway three times and the worker three times, which multiplies into 27 calls for one failure. Retry at one chosen layer.
</Callout>

- **No jitter**, so retries stay synchronized.
- **Retrying non-idempotent actions** without a key.
- **Retrying permanent errors** forever.
- **Infinite attempts** and no dead-letter path.
- **Ignoring the timeout** of the retried call, so retries pile up while earlier attempts are still running.

## Trade-offs

<Callout kind="tradeoff">
Longer backoff protects the dependency but delays recovery for users. More attempts raise the success rate but also load and latency. Idempotency storage adds writes and a table to clean up; skipping it risks duplicate side effects.
</Callout>

## In production

<Callout kind="prod">
Log each attempt with the job id and attempt number, track retry rate and dead-letter size as health signals, set per-dependency limits so one failing service cannot drain all workers, and test a dependency outage on purpose.
</Callout>
