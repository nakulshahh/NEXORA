## Why it exists

"The query is slow" is not a diagnosis. The database already knows how it will run a query. `EXPLAIN` lets you look, so you can fix the actual cause instead of adding indexes at random.

<Callout kind="why">
Performance work is a loop: observe the plan, form a hypothesis, change one thing, observe again. Without the plan you are guessing.
</Callout>

## How it works

A plan is a tree of operations, read from the innermost, most-indented node outwards. Each node shows how rows are produced, and with `ANALYZE` it reports actual time and rows.

```text file=plan.txt mark=1,2,3
Seq Scan on users (actual time=56.645..98.465 rows=1 loops=1)
  Filter: (email = 'user500000@example.com'::text)
  Rows Removed by Filter: 1000000
Execution Time: 98.491 ms
```

Read it: the database scanned the table, threw away a million rows and kept one. "Rows Removed by Filter" in the millions beside `rows=1` is the signature of a missing index.

After creating an index on `email`:

```text file=plan2.txt mark=1
Index Scan using users_email_idx on users (actual time=0.028..0.029 rows=1 loops=1)
Execution Time: 0.036 ms
```

### Common nodes

- **Seq Scan**: read every page. Good when you need most rows.
- **Index Scan**: walk the index, fetch each matching row from the table.
- **Bitmap Heap Scan**: collect matching row locations from an index first, then read the pages in order. Used when many rows match, like the 200 001-row country filter, which still read all 22 213 pages.
- **Joins**: nested loop, hash join, merge join, chosen by the planner from size estimates.

Add `BUFFERS` to see page hits (found in memory) and reads (from disk).

### Estimates versus reality

The planner uses **statistics** about each table to guess row counts. When "estimated rows" and "actual rows" differ by orders of magnitude, the plan is probably wrong because the statistics are stale or the columns are correlated. `ANALYZE tablename` refreshes statistics (autovacuum normally does it).

### A safe loop

1. Capture the slow query and run `EXPLAIN (ANALYZE, BUFFERS)` on realistic data (a tiny dev table lies).
2. Find the node with most of the time or the biggest estimate error.
3. Change one thing: add an index, rewrite the predicate, refresh statistics.
4. Run it again and compare. Keep the change only if the numbers improved.

## Common mistakes

<Callout kind="mistake">
Running EXPLAIN ANALYZE on an UPDATE or DELETE in production. It executes the statement. Use `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`.
</Callout>

- **Tuning on tiny local data**, where a scan is always the fastest plan.
- **Reading only the total time** instead of the node where it is spent.
- **Ignoring estimate-versus-actual mismatches**, the cheapest clue to a bad plan.
- **Changing several things at once**, so you cannot tell what helped.

## Trade-offs

<Callout kind="tradeoff">
EXPLAIN ANALYZE gives the truth but costs a real execution and adds some measurement overhead; plain EXPLAIN is free but only an estimate. Forcing plans with planner settings can fix one query and hurt others, so use it to experiment, not as a permanent fix.
</Callout>

## In production

<Callout kind="prod">
Enable slow-query logging and a statements-statistics extension to find the worst queries by total time, capture plans for them, and review after schema or data growth changes. Store the before and after numbers in the pull request that adds an index.
</Callout>
