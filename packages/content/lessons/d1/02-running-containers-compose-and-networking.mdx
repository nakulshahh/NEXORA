## Why it exists

A single container is a toy; real systems are an API, a database, a worker and a cache that must start in the right order, reach each other, keep data and be reproducible on every laptop. Compose captures that as a file.

<Callout kind="why">
Containers are cattle, not pets: you can delete and recreate any of them. That only works if state, configuration and addresses live outside the container.
</Callout>

## How it works

### Where state lives

A container's own filesystem is thrown away with the container. For data that must survive use a **volume** (managed by Docker, the right choice for database data) or a **bind mount** (a host folder, handy for source code in development). Configuration comes from **environment variables** (B11); logs go to standard output so the platform can collect them.

### Ports and networks

Containers on the same user-defined **network** reach each other by **service name**: the API connects to `db:5432`, not `localhost`. A container's ports are private until you **publish** them: `-p 8080:4000` maps host port 8080 to container port 4000. Publish only what must be reachable from outside; the database should be on the internal network only.

### Compose

This project's `docker-compose.yml` describes the whole stack. The important idea is ordering by *health*, not by start:

```yaml file=compose.yml mark=3,4,5,9,10
services:
  db:
    image: pgvector/pgvector:pg16
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U postgres"], interval: 5s }
  migrate:
    depends_on: { db: { condition: service_healthy } }
  api:
    depends_on:
      migrate: { condition: service_completed_successfully }
```

`db` is "healthy" only when it accepts connections; `migrate` runs once and must succeed; `api` starts only after that. `docker compose up --build` is then the whole system, and `docker compose down -v` removes containers and volumes for a clean slate.

**Verification status:** as noted in the previous lesson, there was no Docker daemon in the development sandbox, so this file was checked by reasoning and by running each step by hand, not by `docker compose up`. If it fails on your machine, the logs below will say why, and a report helps fix it.

### Debugging containers

- `docker compose ps` and `docker ps -a`: state and **exit codes** (137 means killed, often out of memory or after the stop timeout; 143 means stopped by SIGTERM; 1 usually an application error).
- `docker logs -f SERVICE`: standard output and error.
- `docker exec -it SERVICE sh`: a shell inside a running container (slim images may lack tools).
- `docker inspect`: environment, mounts, networks, health status.
- "Connection refused" between services: check the hostname (service name, not localhost), that the dependency is listening on `0.0.0.0` (not `127.0.0.1`), and that both are on the same network.
- A container restarting in a loop: read the last logs before the restart; often a missing environment variable failing config validation, which is exactly the fail-fast behaviour you wanted.

## Common mistakes

<Callout kind="mistake">
Binding the server to `127.0.0.1` inside the container. It is then unreachable from outside the container even with the port published. Listen on `0.0.0.0`.
</Callout>

- **Using localhost to reach other services.**
- **Writing data inside the container** and losing it on recreate.
- **Publishing the database port** to the world.
- **Assuming depends_on means ready.**
- **A `restart: always` policy hiding a crash loop** nobody looks at.

## Trade-offs

<Callout kind="tradeoff">
Compose is excellent for development and small single-host deployments and does not provide multi-host scheduling, rolling updates or self-healing at scale, which is what orchestrators such as Kubernetes add, with considerable complexity.
</Callout>

## In production

<Callout kind="prod">
Treat Compose as a development and small-scale tool, keep volumes backed up (the restore drill applies), set resource limits, collect container logs centrally, and keep the same image from CI through staging to production, changing only environment configuration.
</Callout>
