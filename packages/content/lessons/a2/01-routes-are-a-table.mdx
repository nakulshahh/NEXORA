## Why it exists

After the HTTP request is parsed you have a method such as `GET` and a path such as `/users/42/posts`. Something must decide which of your functions should run. Hard-coding a giant `if` over strings does not scale, so every framework keeps a **route table**: a list of (method, pattern, handler) entries.

<Callout kind="why">
Routing separates "what URL was asked for" from "what code answers it", so you can add an endpoint without touching the others.
</Callout>

## How it works

### Patterns and parameters

A pattern is a path with holes. `/users/:id` has a hole called `id`. To match, split into segments: literal segments must be equal, `:name` segments accept any non-empty text without a slash, and the captured text becomes a **parameter**.

```js file=router.mjs mark=2,3,4,5,6,7,8,9
function compile(pattern) {
  const names = [];
  const re = pattern.split("/").map((seg) => {
    if (seg.startsWith(":")) { names.push(seg.slice(1)); return "([^/]+)"; }
    return seg.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
  }).join("/");
  return { regex: new RegExp(`^${re}$`), names };
}

export function createRouter() {
  const routes = [];
  return {
    add(method, pattern, handler) { routes.push({ method, ...compile(pattern), handler }); },
    match(method, rawPath) {
      const path = rawPath.split("?")[0];
      const allowed = new Set();
      for (const r of routes) {
        const m = r.regex.exec(path);
        if (!m) continue;
        if (r.method !== method) { allowed.add(r.method); continue; }
        const params = Object.fromEntries(r.names.map((n, i) => [n, decodeURIComponent(m[i + 1])]));
        return { status: 200, handler: r.handler, params };
      }
      return allowed.size ? { status: 405, allow: [...allowed] } : { status: 404 };
    },
  };
}
```

That is a working router in about twenty lines. The query string is cut off first because it is not part of the path. Parameters are percent-decoded, so `/users/a%2Fb` gives the id `a/b`.

### 404 versus 405

If no pattern fits the path, the answer is **404 Not Found**. If the path fits at least one pattern but with another method, the answer is **405 Method Not Allowed**, with an `Allow` header naming the methods that do work. The router above collects those methods while it scans.

### Cost

Scanning the list is O(R) regexp tests for R routes. For a few hundred routes that is microseconds and irrelevant next to a database call. Large frameworks compile all routes into a **trie** (a tree keyed by path segment) so lookup depends on the URL's length, not the number of routes.

## Common mistakes

<Callout kind="mistake">
Returning 404 for a valid path with the wrong method. Clients and developers lose the hint that the URL is right and only the verb is wrong. Return 405 with an Allow header.
</Callout>

- **Forgetting that parameters are strings.** The `id` is `"42"`, not `42`. Convert and validate it.
- **Trusting decoded parameters.** `decodeURIComponent` can produce `/`, `..` and other surprises. Never join a parameter into a file path without validating it.
- **Throwing on bad encoding.** `decodeURIComponent("%E0%A4%A")` throws. A hostile URL must produce a 400, not a crash.

## Trade-offs

<Callout kind="tradeoff">
A route table is simple, explicit and easy to read, but in a list the first match wins, so order matters (next lesson). Declarative routing (file-system routes, decorators) hides the table but does not remove the rules.
</Callout>

## In production

<Callout kind="prod">
Frameworks report the matched pattern (such as /users/:id) rather than the raw URL to logs and metrics. Raw URLs contain ids and create millions of distinct metric labels; the pattern keeps the cardinality small and the dashboards usable.
</Callout>
