## Why it exists

Clients and servers written by different people, in different languages, years apart, need to agree on how to ask for something and how to answer. **HTTP** is that agreement: a small set of rules for a request and a response, simple enough to implement in an afternoon and general enough to carry web pages, JSON APIs and file downloads.

<Callout kind="why">
Keeping the protocol text-based and stateless made it easy to debug, cache and scale. Any server can answer any request, so you can put many servers behind one address.
</Callout>

## How it works

### The shape of a message

Here is a complete request, exactly as it travels over the wire. Lines end with `\r\n`, and a blank line ends the headers.

```http file=request.txt mark=1,2
GET /users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
User-Agent: demo/1.0

```

- The **request line**: method, target, version.
- **Headers**: `Name: value` metadata. `Host` is required in HTTP/1.1 because one IP can serve many sites.
- An empty line.
- An optional **body**, whose length is declared by a header.

The response mirrors it:

```http file=response.txt mark=1
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"id":42,"name":"Ada Lovelace"}
```

The **status line** replaces the request line. Then headers, a blank line, and the body.

### How does the reader know where the body ends?

TCP is a byte stream, so HTTP must say. Either `Content-Length: N` gives the exact byte count, or `Transfer-Encoding: chunked` sends the body in length-prefixed pieces, ending with a zero-length chunk. No framework can guess this; it is part of the protocol.

### Speaking HTTP with a raw socket

```js file=raw-http.mjs mark=5,6,7
import net from "node:net";

net.createServer((socket) => {
  let buf = "";
  socket.on("data", (c) => {
    buf += c;
    const end = buf.indexOf("\r\n\r\n");
    if (end === -1) return; // headers not complete yet
    const [requestLine, ...headerLines] = buf.slice(0, end).split("\r\n");
    const [method, target] = requestLine.split(" ");
    const host = headerLines.find((h) => h.toLowerCase().startsWith("host:"));
    const body = JSON.stringify({ method, target, host });
    socket.end(
      `HTTP/1.1 200 OK\r\nContent-Type: application/json\r\nContent-Length: ${Buffer.byteLength(body)}\r\nConnection: close\r\n\r\n${body}`,
    );
  });
}).listen(8080);
```

Run it and `curl -i localhost:8080/hello`. The same server in Node's `http` module is five lines, but it does exactly this parsing for you, plus all the edge cases this toy ignores (partial buffers, request bodies, pipelining, malformed input).

### Statelessness

The server keeps nothing about you between requests. If request two depends on request one, the client must say so: a cookie, an `Authorization` header, an id in the URL. This is why any replica can serve any request.

## Common mistakes

<Callout kind="mistake">
Wrong `Content-Length`. Too small and the client truncates your response. Too large and it hangs waiting for bytes that never come. Count **bytes**, not characters: `"é"` is one character and two bytes in UTF-8.
</Callout>

- **Forgetting the blank line** between headers and body.
- **Trusting the client's headers.** `Host`, `X-Forwarded-For` and `Content-Length` are claims, not facts.
- **Putting secrets in the URL.** URLs end up in logs, history and referrer headers.

## Trade-offs

<Callout kind="tradeoff">
Text headers are easy to read and extend but verbose and repeated on every request. HTTP/2 compresses headers and multiplexes many requests over one connection, which removes HTTP-level head-of-line blocking but not TCP's. HTTP/3 moves to QUIC to remove that too. The semantics you learn here stay the same across all three.
</Callout>

## In production

<Callout kind="prod">
You almost never see raw bytes in production, but you will meet their consequences: proxies that enforce header size limits, load balancers that close idle keep-alive connections, and request-smuggling bugs where two parsers disagree about where a message ends.
</Callout>

When a client and a proxy disagree about the body length, an attacker can hide a second request inside the first. This is why strict, boring parsing matters.
